\chapter{Introduction}\label{ch:introduction}

Most online services require users to create an account, so that users have to manage a large number 
of credentials and often reuse the same password for several services. 
These accounts are frequently linked to personal data such as an email address, a phone number or 
even an official identity document. 
Attackers exploit password reuse by testing large collections of leaked credentials against other 
services, an attack known as credential stuffing. 
Credential abuse, the most common initial access vector of the previous year, is down to 13\% of 
more than 22{,}000 confirmed breaches, while the exploitation of vulnerabilities has risen 
to 31\%~\cite{VerizonDBIR2026}. 

To reduce the number of places where credentials are created and stored, \gls{fim} was developed. 
FIM lets users access several \glspl{sp} with a single set of credentials that is managed by an \gls{idp}. 
FIM consolidates authentication behind a single trusted authority. 
When a user wants to access an SP, the SP redirects the user's browser to the IdP. 
The user authenticates with the IdP, which then confirms the user's identity to the SP~\cite{FIMSurvey}. 

Shibboleth, is one of the most widely deployed open-source implementations of this model in the 
research and education sector~\cite{Shibboleth}. 
Under this model, a user authenticates with their organisation's IdP once. 
The IdP then issues cryptographically signed SAML assertions that SPs accept as proof of identity. 
This describes the authentication process under the SAML implementation of Shibboleth. 
Shibboleth also supports an official plugin for OpenID Connect~\cite{ShibbolethOIDC}. 

This architectural property introduces a critical consequence: the IdP becomes a single point of trust 
for the entire federation~\cite{IdPSinglePointOfTrust}. 
A compromised, misconfigured or vulnerable IdP does not affect one application.
It can undermine the security of every relying SP. 
A notable example is the Sunburst supply chain attack~\cite{FireEyeSSC}. 
As Hartl and Derek note, after the initial compromise the attackers obtained the 
trusted certificate used for signing SAML assertions and used it to access all 
services within the targeted enterprise~\cite{FormalSecAnalysisSAML}. 
Since tokens forged with this certificate carry the organisation's own trusted signature, 
the resulting anomalies may go unnoticed~\cite{MicrosoftBlogSSC}. 
Beyond targeted attacks, SAML deployments are exposed to weaknesses in the protocol and in its 
implementations. 
Somorovsky et al. found \gls{xsw} vulnerabilities in eleven of fourteen SAML frameworks, including 
Shibboleth, which allow an attacker to inject forged claims that the SP accepts once the signature 
has been validated~\cite{BreakingSAML}, and the attack has since been reproduced in other 
OpenSAML-based setups~\cite{VulnerSAMLCloud}. 
In a formal analysis of Shibboleth, Sommer identified three further attacks, namely Response 
Injection, Leaked Assertion Artifact and IdP Spoofing, which let an attacker log a victim into an 
account controlled by the attacker or reuse a leaked artifact to log in as the victim. 
The Shibboleth developers attribute the first of these to the SAML standard itself rather than to 
the implementation~\cite{SecAnalysisSSO}.

Despite this elevated risk profile, systematic security monitoring at the application layer of Shibboleth 
IdP deployments remains largely absent. 
Existing approaches such as AAIEye~\cite{MonitoringAAI} focus primarily on operational availability, 
leaving security-relevant aspects unaddressed. 
The research literature reflects a comparable gap. 
A survey of security analyses in federated identity management finds Shibboleth to be among the least 
examined protocols and raises the question of whether this reflects a stronger security posture or merely 
a lower level of attention~\cite{FIMSurvey}. 
Formal analyses of SAML likewise remain scarce despite its deployment across government, enterprise and 
education~\cite{FormalSecAnalysisSAML}. 

This thesis addresses this gap by proposing a security-oriented monitoring system that operates 
directly within the Shibboleth application layer. 
It makes application-layer security parameters and authentication workflows visible that are 
otherwise inaccessible from outside the application. 
Rather than testing the deployment actively, the system observes it passively. 
This principle has been applied to the eduroam infrastructure by analysing its network 
traffic~\cite{EAPeduroam}, whereas this work applies it inside the application, at the application 
layer of the IdP. 
The system thereby provides federation operators with a continuous view of the security posture of 
their authentication infrastructure. 

Three research questions guide this work:
\begin{itemize}
    \item RQ1 Which security-relevant data can be collected at the application layer of a Shibboleth IdP, and through which mechanisms are these data accessible?
    \item RQ2 How can these data be correlated in order to detect configuration weaknesses and anomalies in the authentication process?
    \item RQ3 What measurable overhead does the resulting system impose on the monitored IdP?
\end{itemize}

The remainder of this thesis is structured as follows. 
\begin{itemize}
    \item Chapter~\ref{ch:background} introduces the technical foundations of FIM, SAML and the Shibboleth IdP.
    \item Chapter~\ref{ch:related-work} positions this work within existing research on application layer intrusion detection and delimits it from network and host based monitoring systems.
    \item Chapter~\ref{ch:system-design} presents the architecture of the proposed system.
    \item Chapter~\ref{ch:implementation} describes its implementation, divided by layer.
    \item Chapter~\ref{ch:evaluation} evaluates the correlation, the detection rules and the overhead of the system.
    \item Chapter~\ref{ch:discussion} interprets the results with respect to the research questions and discusses the limitations of the approach.
    \item Chapter~\ref{ch:conclusion} summarises the findings.
\end{itemize}
