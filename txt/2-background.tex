\chapter{Background}\label{ch:background}

This chapter explains key concepts and terminalogy relevant to this thesis.
It establishes the theoretical and technical foundation necessary for understanding the development of 
the proposed monitoring tool.
The contents are structured as follows: Section~\ref{sec:fim} introduces the concept of Federated Identity 
Management and describes the roles of the Identity Provider and Service Provider, including their interaction 
during the authentication process. 
Section~\ref{sec:shibboleth} introduces Shibboleth as an open-source implementation of SAML, with a 
particular focus on the Shibboleth IdP, which is highly relevant to this thesis. 
Finally, Section~\ref{sec:saml} provides an overview of the SAML framework and its role in 
federated authentication.

\section{Technical Foundation of Federated Identity Management}\label{sec:fim}

As already mentioned in the introduction, FIM allows users to access all their resources they 
need by using a single digital identity. 
It provides \acrfull{sso} functionalities across all applications of an organization. 
Through the properties granted by incorporating SSO into the federation, it eliminated the need 
to create, remember and manage multiple usernames and passwords for users and the organization. 
By centralising identity management, the number of systems holding credentials is 
reduced. 
Fewer accounts and identity management systems means fewer vectors to attack and credential of a 
user to steal~\cite{NIST80063C}. 
It also eases the identity management by centralizing it on a server. 
This centralisation introduces new risks. 
FIM relies on a foundation of trust between organizations and this trust is heavily reliant on 
the security of the IdP. 
The centralization by incorporating an IdP means it creates a single point of trust, 
or in different words, it concentrates the risk onto a single server~\cite{IdPSinglePointOfTrust}. 

A compromise of a primary IdP could potentially grant broad unauthorised access across the 
entire federation. 
This characteristic requires both the IdP and SP to maintain a high level of security~\cite{NIST80063C}. 
The policies defined for each SP in the IdP must accurately translate to the rules 
at the corresponding SP. 
The configuration of the IdP and that of each SP must remain consistent with one another. 
Certificates, keys and protocol settings are maintained separately on both sides, and a mismatch between 
them can weaken the security of a transaction without either party noticing.
To better understand the interaction within a federated identity system, the roles and responsibilities of 
the IdP and SP are described in the following.

A federation consists of two kinds of participants. 
The IdP authenticates users and issues statements about them~\cite{SAMLOverview}. 
The SP offers the resource a user wants to reach and relies on those statements instead of authenticating 
the user itself. 
Neither role is meaningful without the other, and their interaction follows a fixed pattern. 

When a user requests a protected resource, the SP does not check credentials. 
It determines which IdP is responsible for the user and redirects the browser there together 
with an authentication request~\cite{SAMLOverview}. 
The IdP authenticates the user by whatever means the deployment provides, and returns a signed statement 
asserting that the authentication took place and describing the user by a set of attributes. 
The SP verifies the signature, evaluates the statement and grants or denies access on that basis. 
The credentials themselves never leave the IdP.

This division has a consequence for how a federation is configured. 
Because the IdP serves many SPs, it does not treat them uniformly. 
It maintains a separate configuration for each partner, specifying for instance whether the statement 
is to be encrypted, which authentication methods are permitted, and which attributes are released. 
The SP maintains its own configuration in turn, stating what it expects to receive and what 
it will accept.

Both sides therefore hold configuration that describes the same relationship, and both are 
maintained independently. 
What binds them together is the metadata each party publishes about itself: the endpoints at which 
it can be reached, and the certificates by which its statements can be verified. 
Trust within a federation rests on these metadata being current and correctly exchanged~\cite{SAMLMetadata}. 
Whether the two configurations remain consistent with one another, however, is not something the 
protocol itself verifies.

\section{Shibboleth}\label{sec:shibboleth}

Shibboleth is a free and open-source web single sign-on software suite that 
implements SAML and other standards for FIM. 
It is widely used in federated authentication environments and places particular 
emphasis on privacy and decentralized identity management. 
The Shibboleth Consortium provides separate software components for the IdP and 
SP, enabling organizations to participate in federated identity infrastructures~\cite{Shibboleth}.

For the scope of this thesis, the Shibboleth IdP is of particular relevance, as it 
is responsible for authenticating users and issuing SAML assertions to participating 
SPs. 
The IdP is implemented as a Java-based web application and is typically deployed 
using a Java servlet container such as Apache Tomcat. 
User identities and associated attributes are commonly managed through an external 
directory service, such as a Lightweight Directory Access Protocol (LDAP) server, 
which provides the IdP with the information required for authentication and 
attribute release.
It builds on the OpenSAML library for the construction and validation of SAML messages, which is relevant 
because vulnerabilities reported for OpenSAML apply to Shibboleth deployments 
as well~\cite{ShibbolethGIAC}.

\subsection{Profile Flows and Interception Points}\label{subsec:profile-flows}

The IdP processes each request as a workflow built on Spring Web Flow. 
Every top-level flow implements one of the supported protocol interfaces, referred to as profiles, such 
as SAML 2 SP-initiated SSO. 
Within a top-level flow, reusable subflows carry out recurring tasks such as 
authentication~\cite{ShibProfileHandling}.

To allow deployers to extend this behaviour without copying or editing the internal flow definitions, 
the IdP provides a set of defined hooks. 
A subflow attached to such a hook is called an interceptor, and three hooks exist: 
\begin{enumerate}
    \item inbound message processing
    \item post-authentication processing and
    \item outbound message processing
\end{enumerate}
The first and third are available in any profile flow, whereas the second applies only to profiles that 
actually authenticate a user~\cite{ShibProfileHandling}.
An interceptor is registered as a bean and enabled by adding its flow identifier to the corresponding list 
property of a profile configuration in \texttt{conf/relying-party.xml}. 
No modification of the IdP source code is required.

The choice of hook determines what an interceptor can observe. 
An inbound interceptor sees the incoming message context but not the outcome of authentication, 
since that has not yet taken place. 
An outbound interceptor sees the state of the tree produced by the profile execution, including the 
outgoing message. 
The post-authentication hook runs in the middle of processing, after the user has been authenticated but 
before the outgoing message is constructed. 
It can therefore observe both the incoming request and the authentication result, but not the response that 
is issued afterwards.

\subsection{The Context Tree}\label{subsec:context-tree}

The root of the context tree for any profile flow is the \texttt{ProfileRequestContext}. 
It carries the state of a request through the sequence of steps and is the object an interceptor receives. 
Attached to it are child contexts holding the inbound and outbound messages, the identity of the relying 
party and whether that identity could be verified, and, once authentication has completed, the authenticated 
subject~\cite{ShibProfileHandling}.

\subsection{Audit Logging}\label{subsec:audit-logging}

The IdP writes one line per completed transaction to \texttt{idp-audit.log}. 
The set of fields is not fixed but defined by the deployer in \texttt{conf/audit.xml}, so the 
information available in the log depends on the configuration of the individual 
deployment. 
Authentication attempts that do not result in a completed transaction, in particular failed password 
validations, produce no entry in this log~\cite{AuditLoggingConfiguration}. 

\subsection{Configuration}\label{subsec:config}

Three configuration files are relevant in the following. 
\texttt{relying-party.xml} holds the per-partner configuration described in Section~\ref{sec:fim}, 
including which profiles are enabled and which security settings apply~\cite{RelyingPartyConfiguration}. 
\texttt{metadata-providers.xml} declares where the \acrshort{idp} obtains metadata for 
its partners~\cite{MetadataConfiguration}. 
\texttt{attribute-filter.xml} governs which attributes are released to which 
relying party~\cite{AttributeFilterConfiguration}.

\section{SAML}\label{sec:saml}

The \acrfull{saml} is an XML-based standard developed by the organization for the Advancement of 
Structured Information Standards (OASIS) for the exchange of authentication, authorization, and other 
security-related information between different parties.
SAML is a fundamental component of FIM and is widely used to enable SSO across organizational and 
security boundaries~\cite{SAMLOverview}. 
The second major version, SAML 2.0, was published by OASIS in March 2005~\cite{SAML2Standard}.
SAML 1.1 had already gained widespread adoption in federated identity environments~\cite{SAML1Standard}. 
However, several competing approaches existed at the time, including the Identity Federation Framework 
(ID-FF) developed by the Liberty Alliance and the Shibboleth architecture~\cite{SAML2Standard}. 
SAML 2.0 consolidated several of these approaches into a common standard and introduced additional 
capabilities, particularly with regard to federation, interoperability, and privacy. 

\subsection{SAML Assertions}\label{subsec:assertions}

SAML assertions serve as security tokens that convey security-related information about a principal, 
such as a user, system, or service. 
An assertion contains statements made by an issuer about the principal, which may include authentication, 
authorization, and attribute information. 
Since these statements can have security-critical implications, their authenticity and integrity must be 
ensured~\cite{SAMLAssertions}. 
Therefore, the SAML element can be protected by a digital signature following the XML Signature standard, 
allowing a relying party to verify that the assertion was issued by the stated issuer and has not been 
modified.

Each assertion contains metadata that defines its origin and validity. 
The \texttt{Issuer} element identifies the entity that issued the assertion, while the \texttt{IssueInstant} 
attribute specifies the time at which it was issued. 
Furthermore, every assertion is assigned a unique identifier that must not be reused. 
Once an assertion has been issued, the issuer has no direct control over its subsequent use. 
Consequently, a consumer of an assertion is expected to enforce its specified validity conditions, 
including any validity interval and applicable \texttt{OneTimeUse} condition.

\subsection{XML-Signature and Encryption}\label{subsec:xml-sig-enc}

To protect the integrity and authenticity of SAML assertions, XML signatures can be used to 
cryptographically bind the assertion to its issuer. 
The XML Signature standard defines the syntax and processing rules for creating, representing, and 
verifying XML-based digital signatures. 
A signature is represented by the \texttt{Signature} element and can be applied to an entire SAML assertion 
or to selected parts of an XML document~\cite{SAMLAssertions}.

Depending on the location of the signature relative to the signed data, XML signatures can be categorized 
into three types~\cite{W3CXMLSIG}. 
An enveloped signature is contained within the XML element that it signs. 
In contrast, an enveloping signature contains the signed data within the signature itself. 
A detached signature is neither contained within nor a parent of the signed data and references the signed 
content externally. 
In the context of SAML, enveloped signatures are commonly used to sign SAML assertions and protocol 
messages.

XML Encryption provides confidentiality for sensitive information contained in SAML messages. 
Instead of transmitting the original XML content in plaintext, the protected content is replaced by 
an \texttt{EncryptedData} element containing the resulting ciphertext~\cite{W3CXMLENC}. 
XML Encryption therefore enables selective and persistent confidentiality of individual elements within 
an XML document. 
This allows, for example, sensitive attributes contained in a SAML assertion to be encrypted without 
requiring the entire message to be encrypted.

Although XML Signature and XML Encryption provide important security mechanisms, their use and 
configuration depend on the respective SAML profile, deployment, and implementation. 
SAML is therefore not a security protocol in itself, but a framework whose optional features can be 
composed in different ways, and the resulting security properties follow from the composition chosen. 
Hartl and Derek make this explicit by deriving eight protocol variants from the optional features 
of a single use case and analysing each separately~\cite{FormalSecAnalysisSAML}. 
Consequently, the security properties of a SAML-based system cannot be derived solely from the existence 
of these mechanisms in the standard. 
Incorrect configuration or implementation may result in insufficient protection, such as assertions that 
are not appropriately signed or sensitive information that is transmitted without encryption.

\subsection{SAML Bindings}\label{subsec:saml-bindings}

SAML bindings define how SAML protocol messages are transported using underlying 
communication protocols. 
They are particularly relevant for the Web Browser SSO profile, where the user's web 
browser acts as an intermediary between the IdP and SP. 
The SAML specification defines several bindings for different communication scenarios. 
In a typical SP-initiated Web Browser SSO process, the HTTP-Redirect and HTTP-POST 
bindings are particularly relevant~\cite{SAMLBinding}.

\subsubsection{HTTP-Redirect Binding}

The HTTP-Redirect binding is designed for scenarios in which SAML requester and 
responder communicate through an HTTP user agent acting as an intermediary. 
In the SP-initiated SSO flow, the SP acts as the SAML requester and the IdP as the 
SAML responder. 
The authentication request is encoded and transmitted as part of the URL query string 
of an HTTP redirect. 
The user's browser follows the redirect and thereby forwards the request to the IdP.

Since the message is transported through the URL using the HTTP GET method, the 
binding is particularly suitable for relatively small SAML messages, such as an 
authentication request. 
The HTTP-Redirect binding therefore provides the mechanism by which the SP can 
initiate the authentication process without requiring a direct communication channel 
between the SP and IdP.

\subsubsection{HTTP-POST Binding}

The HTTP-POST binding is likewise designed for communication between a SAML requester 
and responder through an HTTP user agent. 
In the return direction of the typical SP-initiated SSO flow, the IdP transmits the SAML 
response to the SP. 
The SAML response is embedded in an HTML form and sent to the SP using the HTTP POST method.
The user's browser acts as an intermediary by submitting the form to 
the SP. 

Compared with the HTTP-Redirect binding, HTTP-POST is better suited for larger SAML 
messages because the message is not encoded into the URL. 
This makes it particularly suitable for SAML responses containing assertions and 
associated security-related information. 

\subsection{Web Browser SSO Authentication Process}\label{subsec:sso-auth-process}

The SAML Web Browser SSO profile enables a user to authenticate to an IdP and subsequently access a 
protected service provided by a SP. 
The process is mediated by the user's web browser, which forwards SAML messages between the SP and IdP.

The process begins when a user requests access to a protected resource at the SP. 
If the user does not have an established session, the SP generates a SAML authentication request and 
redirects the user's browser to the IdP. 
The IdP processes the request and authenticates the user using the configured authentication mechanism. 
Upon successful authentication, the IdP generates a SAML response containing a SAML assertion with 
security-related statements about the authenticated principal.

The assertion can be digitally signed by the IdP to provide authenticity and integrity. 
The SAML response is then returned to the user's browser, which forwards it to the SP. 
The SP validates the received SAML response and assertion, including the digital signature and the 
applicable validity conditions. 
If the assertion is considered valid, the SP evaluates the contained statements and attributes to 
determine whether the user is authorized to access the requested resource. 
If the authorization requirements are satisfied, the SP grants the user access to the protected 
service~\cite{SAMLOverview}.

The use of the user's web browser as an intermediary introduces an important security consideration. 
The SAML messages exchanged between the IdP and SP are transmitted through the user's browser and 
therefore pass through a communication path that is not directly controlled by either party. 
Neither the IdP nor the SP can assume that the messages remain unchanged while being forwarded. 
Consequently, the security of the protocol cannot rely solely on the communication channel. 
Instead, mechanisms such as digital signatures, message identifiers, validity conditions, and audience 
restrictions are used to ensure the authenticity and integrity of SAML messages and to 
prevent their misuse.

An important security property of this process is the prevention of message replay. 
SAML requests and assertions contain unique identifiers that allow the SP and IdP to assign messages 
and detect previously processed messages. 
In particular, an assertion's unique identifier must not be reused, and the recipient is expected to 
enforce the applicable validity conditions and replay-related constraints. 

\subsection{SAML Metadata}\label{subsec:saml-metadata}

SAML metadata provides a standardized way for SAML entities to describe their configuration and 
capabilities to other participating entities. 
It enables IdPs and SPs to obtain information required for establishing communication and processing 
SAML messages without requiring every configuration parameter to be exchanged manually. 
The SAML metadata specification organizes this information around roles supported by an entity, 
which are represented using role descriptors within an \texttt{EntityDescriptor} element~\cite{SAMLMetadata}.

For an IdP, the \texttt{IDPSSODescriptor} describes information relevant to its role as a SAML IdP. 
Similarly, an SP can be described using an \texttt{SPSSODescriptor}. 
These descriptors contain information such as supported SAML protocols, communication endpoints, 
supported bindings, and cryptographic keys. 
For example, an SP metadata document can specify its Assertion Consumer Service (ACS) endpoint and the 
bindings supported for receiving SAML responses, while an IdP can specify its SSO Service endpoints and 
the corresponding supported bindings.

Cryptographic information contained in metadata is particularly important for the security of SAML 
communication. 
Metadata can contain certificates and public keys used by participating entities for verifying digital 
signatures or encrypting SAML messages. 
Consequently, the metadata configuration directly influences how SAML messages are validated and which 
endpoints and cryptographic keys are considered valid by an implementation.

The security of the metadata itself is therefore an important aspect of a SAML deployment. 
If an entity accepts manipulated metadata, an attacker could potentially influence endpoints, 
supported bindings, or cryptographic keys used during SAML message processing. 
SAML metadata can itself be protected using digital signatures, allowing an entity to verify the integrity 
and origin of the metadata before using it for configuration or trust decisions.
