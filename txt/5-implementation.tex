\chapter{Implementation}\label{ch:implementation}

This chapter describes the implementation of the proposed monitoring tool and 
discusses the main challenges encountered during development. 
It follows the same structure as Chapter~\ref{ch:system-design} by examining 
each system layer and describing its technical implementation. 

\section{Data Aggregation Layer}\label{sec:impl-aggregation}

As described in Section~\ref{sec:data-aggregation}, the data aggregation layer 
uses log shippers to collect and parse log entries and static configuration 
files, as well as a custom interceptor that operates within the Shibboleth IdP. 
The log shipping stack consists of Filebeat for reading the source files and 
Logstash for preprocessing and transmitting the collected data. 
Both components are deployed on the IdP side. 

A key aspect of the implementation is the handling of audit log entries. 
Instead of parsing the audit log according to a fixed format, Logstash processes 
the audit fields as key-value pairs. 
This provides the technical basis for adapting to changes in the configured audit 
format and enables the monitoring system to handle the dynamic structure of the 
audit logs. 

The monitoring tool handles these dynamic changes by maintaining a field registry. 
The registry periodically retrieves the most recent audit entries stored in the 
database and extracts the names of all fields that are currently present. 
Using only recent entries ensures that fields no longer written by the IdP are 
eventually removed from the registry. 
Both the detection rules and the correlation strategies query the registry before 
they are applied, which is how the withdrawal described in 
Section~\ref{subsec:detection} is realised in practice. 

The audit log is not the only log file read by the collection layer. 
As described in Section~\ref{subsec:audit-log}, authentication attempts that do not 
result in a completed transaction produce no entry there, which applies in particular 
to failed password validations. 
The Shibboleth IdP writes these events to separate files, \textit{idp-password-audit.log} 
and \textit{idp-mfa-audit.log}, which record the outcome of the corresponding 
authentication flows. 
Filebeat is configured to read these files in addition to the general audit log, and the 
Logstash pipeline tags the resulting records with their source so that they remain 
distinguishable in the backend. 
Without this second source, the rules that evaluate failed authentication attempts would 
have no data to operate on. 

A particular difficulty of this mechanism is that a missing field does not manifest 
itself as an error. 
If the audit format of a deployment does not include a field that a rule depends on, 
no exception is raised and no entry is written to any log. 
The information is simply absent, and a rule evaluating it would silently operate on 
incomplete data. 
The registry therefore does not only serve adaptability, but also makes this absence 
explicit and detectable. 

The static configuration files are collected by the same log shipping stack, but 
processed differently. 
Unlike the audit log, which is written continuously and line by line, 
\textit{relying-party.xml} and the metadata documents change rarely and are read 
as a whole. 
Filebeat is therefore configured to aggregate the lines of such a file into a single 
event before transmitting it, and Logstash forwards the result without field level 
parsing. 
The number of lines combined in this way is bounded by configuration, which places an 
upper limit on the size of a document that can be transmitted as a unit. 
The interpretation of the XML structure takes place in the monitoring tool itself, 
where the relevant security settings are extracted and stored per SP. 

Unlike the log shippers, the interceptor is a custom component developed as part of 
this work. 
It is registered as a Spring bean within the Shibboleth IdP and activated through the 
\texttt{postAuthenticationFlows} property of the corresponding profile configuration. 
The interceptor therefore integrates into the IdP without any modification of its 
source code, which is how the third requirement of Section~\ref{sec:requirements} is met. 

The interceptor extends the \texttt{AbstractProfileAction} API of the Shibboleth IdP and 
operates on the \texttt{ProfileRequestContext}, which represents the current state of the 
profile execution~\cite{AbstractProfileAction, ProfileRequestContext}. 
From this context it accesses the child contexts that carry the information relevant to 
the monitoring purpose. 
The \texttt{RelyingPartyContext} identifies the SP for which the authentication is 
performed, the \texttt{SubjectContext} provides the authenticated subject, and the 
\texttt{InboundMessageContext} gives access to the raw SAML request as it was 
received~\cite{RelyingPartyContext, SubjectContext, InOutOperationContext}. 
Further contexts, among them the \texttt{AuthenticationContext} and the 
\texttt{SessionContext}, supply information about the authentication flow that was used 
and the session state at the time of the request~\cite{AuthenticationContext, SessionContext}. 

The information obtained from these contexts is extracted, parsed, and combined into 
a single payload. 
Before this payload leaves the IdP, the sensitive identifiers it contains are 
pseudonymised, as required by the design described in Section~\ref{sec:trust}.

The implementation of this step is complicated by the fact that it takes place in two 
different components. 
The interceptor pseudonymises the identifiers it collects within the Java application, 
whereas the audit fields are pseudonymised by Logstash during preprocessing. 
Both must produce the same value for the same identifier, since the correlation described 
in Section~\ref{subsec:correlation} relies on comparing hashed subjects and addresses 
across the two sources. 
A mismatch would not cause an error but would silently prevent records from being matched.
Both components therefore apply the same hash function and share the same secret salt. 
The salt is provided through the deployment configuration rather than embedded in either 
component, so that it can be rotated without modifying the interceptor or the Logstash pipeline.

\section{Transport Layer}\label{sec:impl-transport}

Before the aggregated data is transmitted, the collecting component authenticates itself to 
the monitoring tool using an HMAC signature, as outlined in Section~\ref{sec:trust}. 
Both Logstash and the interceptor hold the shared secret and sign the records they send, 
so that the backend can verify that a received message originates from an authorised collection 
component.

The verification is conditional on configuration. 
If no secret is configured on the sending side, the message is transmitted unsigned, and the 
backend enforces validation only where a secret has been configured there as well. 
This makes it possible to deploy the system without prior key distribution, for instance in a 
test environment, at the cost of accepting unauthenticated records in that case. 
A production deployment is therefore expected to configure the secret on both sides. 

The monitoring tool provides a separate endpoint for each type of collected data. 
An interceptor report, an audit entry and a configuration document differ in structure and in the 
processing they require, so that separating them at the interface avoids having to determine the 
type of a record before it can be handled.

As mentioned in Section~\ref{sec:trust}, the interceptor sends the payload asynchronously. 
The interceptor does not wait for a response from the monitoring tool and proceeds with the 
authentication flow immediately after dispatching the record. 
If the transmission fails, whether because the backend is unreachable, the request times out or 
the record is rejected, the interceptor receives no indication of it and the record is lost 
without a trace at its point of origin.

To quantify the cost of this design decision, the interceptor also supports a synchronous mode. 
In this mode it waits for the backend to confirm receipt before the authentication flow continues, 
which makes the time spent on transmission visible in the overall duration of a login. 
The mode is not intended for productive use but serves as a reference point against which 
the asynchronous variant can be compared. 
The resulting measurements are presented in Section~\ref{sec:overhead}.

\section{Correlation and Detection Layer}\label{sec:impl-processing}

This section describes the main technical components of the backend application, 
following the same structure as Section~\ref{sec:processing}.

\subsection{Storage}\label{subsec:impl-storage}

Elasticsearch serves as the primary data store of the backend application. 
The choice follows from the data collection layer described in 
Section~\ref{sec:impl-aggregation}, since Filebeat and Logstash write directly into 
Elasticsearch and no further conversion is required for the data they deliver. 

The application uses separate indices for the different types of data it handles, namely 
audit entries, metadata, configuration data, and interceptor reports. 
These indices differ in how they are created. 
Audit entries are written by Logstash into time based indices that are rotated daily, 
whereas interceptor reports are stored in a single index maintained by the application 
itself. 
Queries that span audit data therefore address an index pattern rather than a concrete 
index, which restricts the set of Elasticsearch operations available for them.

Elasticsearch does not provide relations between documents. 
The result of a correlation is therefore stored as a field on the interceptor report, 
which holds the identifier of the audit entry it was matched with. 
The strategy that produced the match is stored alongside it, as described in 
Section~\ref{subsec:correlation}, so that the basis of a correlation remains visible 
after the fact.

\subsection{Correlation}\label{subsec:impl-correlation}

This section describes how the two challenges of the correlation layer identified in 
Section~\ref{subsec:correlation} are addressed in the implementation, namely the temporal 
offset between the arrival of related records and the varying availability of fields 
in the audit log.
The interceptor report is static and always contains the fields required for correlation. 
The constraint therefore lies entirely on the audit side. 
The audit logging documentation lists all fields that a deployment may 
record~\cite{AuditLoggingConfiguration}, of which four are usable for establishing a 
relationship between an audit entry and an interceptor report. 

\begin{itemize}
    \item \textbf{I}: the inbound message identifier of the SAML request
    \item \textbf{u}: the username, pseudonymised by Logstash
    \item \textbf{a}: the client IP address, pseudonymised by Logstash
    \item \textbf{T}: the timestamp of the event
\end{itemize}

These fields differ in how precisely they identify a counterpart. 
The inbound message identifier is unique per request and therefore establishes the relationship 
unambiguously, since the same value appears in both records. 
The two pseudonymised identifiers narrow the set of candidates to those belonging to the same 
subject and origin, but several logins of the same user may share them. 
The timestamp alone can only indicate temporal proximity. 
In addition, all strategies restrict candidates to the SP recorded in both records, since 
an audit entry for a different partner can never be the counterpart of a given report.
Where the inbound message identifier is not recorded, the relationship can therefore only be 
approximated. 
If none of the identifiers is available, the timestamp remains the sole criterion.

The three correlation strategies implement a common interface and are applied in a fixed order 
of precedence. 
Each strategy declares the audit fields it depends on and queries the field registry described 
in Section~\ref{sec:impl-aggregation} before it is applied. 
Where a required field is not recorded by the deployment, the strategy withdraws and the next 
one in the chain is attempted.

The first strategy, \texttt{INBOUND\_MESSAGE\_ID}, matches the inbound message identifier of 
the interceptor report against the corresponding audit field. 
Since this value is unique per request, a match establishes the relationship without ambiguity. 
The second strategy, \texttt{HASH\_AND\_TIME\_WINDOW}, narrows the candidates by SP, pseudonymised 
subject and pseudonymised client address, and additionally restricts them to a configurable time 
window around the event. 
The third strategy, \texttt{TIME\_WINDOW}, retains only the SP and the time window, and is therefore 
used where neither the message identifier nor the pseudonymised identifiers are recorded. 

The pseudonymised subject appears under two names, since the interceptor report stores it as 
\textit{subjectHash} whereas the audit entry records it as \textit{usernameHash}. 
Both hold the same value, derived from the same identifier with the same salt, and the distinction 
is one of naming within the respective data source rather than of content. 

Both time window strategies may return more than one candidate. 
In this case the entry with the smallest temporal distance to the interceptor report is selected. 
The strategy that produced a match is stored alongside the result, so that the reliability of a 
given correlation remains apparent afterwards. 

The timestamp used for these windows requires particular attention. 
The field that Elasticsearch assigns to an audit document by default reflects the point at which 
Filebeat read the log line, not the point at which the authentication took place. 
Since Filebeat processes log lines in batches, this value is shared by all entries of a batch and 
does not preserve their order. 
The Logstash pipeline therefore derives a dedicated field from the event timestamp recorded by the 
IdP, and both time window strategies operate on this field. 
The effect of this distinction on correlation precision is examined in 
Chapter~\ref{ch:evaluation}.

The temporal offset described in Section~\ref{subsec:correlation} is addressed by repeated 
attempts. 
An interceptor report that could not be correlated on arrival is retried periodically, with a 
minimum age before the first attempt to account for the indexing delay of the log shipping stack. 
After a defined retry window has elapsed without a match, a separate scheduled sweep marks the 
report as permanently uncorrelated. 
This marking is what allows an uncorrelated report to be distinguished from one that is still 
awaiting its counterpart, and thus what makes the proportion of successfully correlated reports 
determinable at all.

Two mechanisms prevent an audit entry from being claimed twice. 
Within a single retry run, entries that have already been assigned are excluded from the candidate 
set of subsequent reports. 
Across runs, the application verifies against the stored data whether an audit entry has already 
been referenced by another report before accepting a match.

\subsection{Detection}\label{subsec:impl-detection}

The detection logic is divided into four engines, following the separation by input type 
described in Section~\ref{subsec:detection}. 
The rule engine evaluates login events derived from audit entries, the configuration rule 
engine evaluates the security settings of a SP, the metadata rule engine evaluates its 
metadata, and the interceptor rule engine evaluates the reports produced by the interceptor. 

All rules implement a common interface. 
A rule receives a single object of the type its engine is responsible for and returns either 
an alert or nothing. 
Each rule additionally declares which fields it depends on, and the engine queries the field 
registry described in Section~\ref{sec:impl-aggregation} before evaluating it. 
Where a required field is not recorded by the deployment, the rule is skipped rather than 
evaluated on incomplete data. 

The engines are executed by a scheduler at intervals that reflect the rhythm of their input. 
Login events and interceptor reports arrive continuously and are therefore evaluated 
frequently, whereas configuration and metadata change rarely and are checked at longer 
intervals. 
To avoid evaluating the same login events repeatedly, the application maintains a marker that 
records the point up to which audit entries have already been processed. 
Each run evaluates only entries newer than this marker, and the marker is advanced once the run 
has completed. 
A grace period is applied before an entry is considered, so that records still being indexed by 
the log shipping stack are not skipped.

A further mechanism concerns repeated findings. 
A weakness in a configuration persists until the operator changes it, and evaluating the same 
configuration every few minutes would otherwise produce a continuous stream of identical alerts. 
The application therefore stores at most one alert of a given type per subject and day, so that 
a persistent condition is reported once rather than repeatedly.

The rules differ in the kind of condition they examine. 
Three examples illustrate this range. 
\texttt{WEAK\_ENCRYPTION} compares the encryption algorithm recorded for a login against a list 
of algorithms considered insecure, which is maintained in the application and can be adjusted 
without changing the rule itself. 
\texttt{BRUTE\_FORCE} does not evaluate a single event in isolation but counts failed 
authentication attempts of the same subject within a defined time window, which requires a query 
across previously stored events. 
\texttt{SIGNATURE\_WRAPPING\_SUSPECTED} operates on the raw SAML request contained in an 
interceptor report and examines its structure for duplicate identifiers and for signature 
elements referencing an identifier that occurs more than once. 

The remaining rules follow one of these patterns or compare an observed event against the 
configuration declared for the SP involved, as described for \texttt{MFA\_BYPASS} in 
Section~\ref{sec:why-not-siem}. 
Their assignment to documented vulnerabilities and attack classes is given in 
Table~\ref{tab:rules}. 

A further difficulty arose with the comparison between configuration and runtime event. 
The authentication flows permitted for a service provider are listed in 
\textit{relying-party.xml} without a namespace prefix, whereas the audit log records the 
flow that was actually used with one. 
The same flow therefore appears as \texttt{MFA} in the configuration and as 
\texttt{authn/MFA} in the audit entry. 
A direct string comparison between the two never matches, and the rule would consequently 
never report a finding. 
The comparison is therefore performed token by token, accepting both notations, and is 
encapsulated in a helper shared by the rules that evaluate authentication flows. 
As with the two cases described in Section~\ref{sec:impl-aggregation}, the failure mode 
here would have been silent, since neither an exception nor a log entry would have 
indicated that the comparison was ineffective. 

\section{Visualization Layer}\label{sec:impl-visualization}

The visualization layer displays the collected, correlated, and detected data through an 
Angular based web application. 
A generic dashboard such as Kibana was not used, since the views required here are specific to 
the domain of the monitoring tool. 
They present findings together with the records from which they were derived and follow the 
relationships that the correlation layer establishes, neither of which can be expressed through 
generic index queries alone. 
The main pages implemented for the web application are described below.

The dashboard provides an overview of the most important data within a specified timeframe. 
It includes the total number of logins, failed logins, successful logins, and detected alerts. 
In addition, it provides a line chart showing the number of logins over the selected timeframe, 
an overview of the total number of logins per SP, and a detailed table of the individual login 
events.

The login overview for each SP also provides a detailed dialog containing the configuration and 
metadata defined for the respective SP in the Shibboleth IdP. 
The SP details further include an overview of any misconfigurations detected by the rule engines 
described in Section~\ref{subsec:impl-detection}.

The second major page of the web application is the alert page. 
As its name suggests, this page displays the recent alerts detected by the monitoring tool. 
It includes a vertical bar chart showing the alerts detected during the current week, grouped by 
their respective severity. 
The page also provides a table of alerts ordered by severity.

Each row in the alert table is interactive and opens a detailed dialog containing information about 
the selected alert. 
This dialog also provides access to the audit entry and the interceptor report associated with the 
alert. 
Conversely, both the audit entry and the interceptor report dialogs list all alerts detected for 
the corresponding event. 
The relationship established by the correlation layer is therefore navigable in both directions, 
which allows an operator to examine a finding together with the records it was derived from rather 
than in isolation.

The audit entry view displays only the information that was available in the corresponding audit 
file of the Shibboleth IdP. 
Since subjects and client addresses are pseudonymised before leaving the IdP, as described in 
Section~\ref{sec:impl-aggregation}, the interface presents these values in their hashed form. 
An operator can therefore recognise that several events originate from the same subject without 
learning the identity of that subject.

Each alert can also be acknowledged by an operator and marked as a false positive. 
Acknowledged alerts and false positives are removed from the default alert view, which only displays 
active alerts.

The third major page displays the collected interceptor reports in a table. 
Each row contains the most relevant information from the corresponding interceptor report and 
indicates whether the report was successfully correlated with an audit entry. 
This makes the state described in Section~\ref{subsec:impl-correlation} visible to the operator, 
including reports for which no counterpart was found within the retry window. 
Each row can be expanded to reveal additional details, including the raw SAML request, and a button 
allows the operator to open the corresponding alert in a detailed dialog.
