\chapter{Evaluation}\label{ch:evaluation}

This chapter evaluates the proposed monitoring system. 
It presents the test setup, evaluates the correlation and detection capabilities, 
measures the performance overhead introduced by the interceptor, and concludes 
with a discussion of the threats to validity. 

\section{Test Setup}\label{sec:setup}

To facilitate integration with the Java testing framework, the entire test environment 
runs in containers. 
This comprises the Shibboleth IdP, an LDAP directory serving as the user store, the SPs, 
and the backend application of the monitoring tool.

Two SPs are deployed. 
The first is used for the detection scenarios and is configured to exhibit the weaknesses 
that the rules are intended to identify. 
The second is configured according to current recommendations and serves as a reference for 
the false positive rate, since any alert raised for a login against this provider is by 
definition a false positive. 

The evaluation distinguishes three levels of testing. 
Unit tests examine individual components in isolation, with their dependencies replaced by 
mocks, so that a test result reflects the behaviour of that component alone. 
Integration tests run against a real Elasticsearch instance, which additionally covers the 
persistence layer, the index mappings and the queries that a mock cannot represent. 
End to end tests exercise the complete pipeline, from a login at the SP through the log 
shipping stack to the alert produced by the backend. 

Logins are generated in two ways. 
An HTTP client harness performs the SAML login sequence directly, parsing the forms returned 
by the IdP and submitting them without rendering the pages. 
Selenium based tests drive an actual browser through the same sequence. 
The two differ in the interval between consecutive logins, since the harness proceeds as fast 
as the server responds whereas a browser adds the time required for page loading and form 
interaction. 
This difference is relevant for the correlation measurements in Section~\ref{sec:eval-correlation}, 
where the temporal density of logins determines how reliably records can be matched.

The environment is not a production deployment. 
It comprises a single IdP, two SPs and a small number of test accounts, and all traffic is generated 
for the purpose of measurement. 
The implications of this are discussed in Section~\ref{sec:validity}.

\section{Correlation}\label{sec:eval-correlation}

Section~\ref{subsec:impl-correlation} described the technical details of the correlation 
mechanism. 
This section presents the results of the correlation and evaluates the precision of the 
individual strategies.

To determine the precision of the less reliable strategies, a reference is required that 
indicates whether a given correlation was correct. 
The correlation via \texttt{INBOUND\_MESSAGE\_ID} establishes a one-to-one relationship, as 
explained in Section~\ref{subsec:impl-correlation}, since the identifier is unique per request. 
Wherever this strategy produced a match, the correct counterpart is therefore known without 
ambiguity, which allows it to serve as a ground truth for the remaining strategies.

The measurement method is as follows:

\begin{itemize}
    \item Collect all interceptor reports of a configurable time period for which 
          \texttt{correlated\_by = INBOUND\_MESSAGE\_ID}
    \item For each report and each window size, execute the exact query of the heuristic 
          strategy and select the same candidate as the productive system would, namely the 
          one with the smallest temporal distance
    \item Compare the selected entry against the known correct audit identifier, classifying 
          the outcome as a match, an incorrect assignment, or no match
    \item Additionally record the temporal offset between the reception of the interceptor 
          report and the actual audit event time as a distribution
\end{itemize}

The underlying data source is 200 consecutive logins of a single test user via the HTTP login 
harness, preceded by three warm-up logins that are included in the measurement. 
In terms of candidate ambiguity this represents the worst case, since all candidates share the 
same \textit{subjectHash}, \textit{ipHash} and SP, leaving time as the only distinguishing 
feature.

\subsection{Defects Identified during the Evaluation}\label{subsec:eval-correlation-findings}

Before the evaluation, 3{,}690 out of 3{,}690 correlations had been established through the 
hashed identity and time window strategy, and not a single one through 
\texttt{INBOUND\_MESSAGE\_ID}. 
The cause was not located in the application but in the audit format of the IdP. 
The \textit{shibboleth.AuditFormattingMap} in \textit{conf/audit.xml} did not contain 
\texttt{\%I}. 
The Logstash pipeline was already mapping \textit{[shib][I]} to the corresponding field, but it 
was waiting for a value that the configuration never produced. 
The precondition of the strategy, namely the presence of the inbound message identifier in the 
field registry, therefore remained permanently unmet. 
After adding \texttt{\%I} to the audit format, the registry recognised the field and the 
strategy activated itself during operation, without restarting the system. 
This is direct evidence of the dynamic field adaptation described in 
Section~\ref{sec:impl-aggregation}.

A second finding concerns the timestamp used by the time window strategies. 
These compared against the \textit{timestamp} attribute, which reflects the ingest time assigned 
by Filebeat rather than the time of the authentication event. 
Since Filebeat processes log lines in batches, this value is shared by all entries of a batch. 
A measurement on benchmark traffic showed that 2{,}423 audit entries were distributed across only 
448 distinct \textit{timestamp} values, an average of 5.4 events per timestamp. 
Within such a group the temporal distance is identical for all candidates, so the chronological 
order of several logins could not be reconstructed.

This was resolved by introducing a dedicated field \textit{event\_time}, which Logstash derives 
from \texttt{\%T}, the event time recorded by the IdP, using a date filter. 
Both time window strategies have operated on this field since. 
The \textit{timestamp} attribute remains the basis for scheduler markers and the indexing grace 
period, where the ingest time is the factually correct reference.

\subsubsection{The Independent Contribution of \textit{ipHash}}\label{subsubsec:influence-of-iphash}

multi-user datasets, or whether \textit{usernameHash} alone accounted for the measured precision. 
The initial assumption had been that all benchmark processes would share a common 
\textit{ipHash}.

\texttt{BrowserWebDriverContainer} started in parallel is assigned its own Docker bridge

The three test users in Section~\ref{subsubsec:precision-multiple-browser-users} therefore had

contribution of \textit{ipHash}.

\subsection{Interpretation of the Results}\label{subsec:interpretation-correlation}

Window size is not the limiting factor. Precision remains at 100\% even though the mean 
number of candidates rises from 6.4 at $\pm$1,s to 197.6 at $\pm$60,s.
Before turning to precision, the coverage of the correlation is considered, that is the 
proportion of interceptor reports for which a counterpart was found at all. 
Across the measured period, 3{,}762 of 3{,}765 reports were correlated, leaving three that 
remained without a counterpart after the retry window had elapsed. 
The value is only determinable because the sweep described in 
Section~\ref{subsec:impl-correlation} marks expired reports as permanently uncorrelated. 
Without that distinction, a report still awaiting its audit entry would be indistinguishable 
from one that will never receive it, and the denominator of the ratio would change with every 
query rather than remaining fixed.

Coverage is also independent of the strategy that produced a match.  
In every measurement reported above it remains at 100\% from a window of $\pm$5\,s onwards, 
including for \texttt{TIME\_WINDOW}, which loses precision but not coverage under high login 
density. 
The two properties therefore fail independently of one another. 
A weaker strategy does not leave reports unassigned, it assigns them to the wrong counterpart.

Window size is not the limiting factor. 
Precision remains at 100\% even though the mean number of candidates rises from 6.4 at 
$\pm$1\,s to 197.6 at $\pm$60\,s. 
What matters is solely that the temporal jitter is smaller than the interval between two 
consecutive logins of the same combination of subject, address and SP.

This yields a quantifiable operational limit. 
With a jitter span of 173\,ms and an observed login interval of approximately 330\,ms, the limit 
lies at about six logins per second per tuple of subject, address and SP. 
Beyond this point the heuristic can no longer resolve the order reliably, whereas the exact 
strategy is unaffected by it.

The measurements also support a concrete configuration recommendation, namely 
\textit{lg.correlation.window-seconds=1}. 
Coverage and precision remain at 100\%, but 6.4 candidates are examined per report instead of 
58.1, which reduces the effort by a factor of nine on the basis of evidence rather than a 
fixed assumption.

The fallback chain has a quantifiable value. 
Where the unique identifier is absent from the audit log, for instance because it is not recorded 
for data protection reasons, the heuristic delivers equivalent results under the measured 
conditions. 
The loss of information is therefore not qualitative but quantitative, and it only takes effect 
above the login density stated above.

The cost of omitting the hashes is thus quantified rather than merely postulated. 
This applies, however, only to the comparison between the exact strategy and 
\texttt{HASH\_AND\_TIME\_WINDOW}. 
If both \textit{ipHash} and \textit{usernameHash} are missing, so that \texttt{TIME\_WINDOW} has 
to step in, the picture changes. 
Section~\ref{subsubsec:precision-time-window-multi-user} shows a drop in precision from 100\% to 
65\% with three simultaneously active users, concentrated on logins less than 100\,ms apart. 
For a SP with several concurrent users, \texttt{TIME\_WINDOW} is therefore to be classified as a 
stopgap for the case of missing hashes rather than as an equivalent alternative, unlike what the 
single user measurement in Section~\ref{subsec:eval-correlation-results} alone would suggest, 
where both strategies are indistinguishable.

There is a first indication that the operational limit is not reached in practice. 
Section~\ref{subsubsec:precision-browser-traffic} measures the login density under real browser 
traffic instead of the synthetic HTTP client harness, and all 202 logins lie more than one second 
apart, well below the limit of roughly six logins per second calculated above. 
For a single automated browser user the synthetic worst case of 
Section~\ref{subsec:eval-correlation-results} is therefore considerably denser than real timing, 
although this has not yet been shown for several concurrent real users.

What matters is the distribution of density, not merely the possibility of a collision. 
Section~\ref{subsubsec:precision-multiple-browser-users} shows that the weakness of 
\texttt{TIME\_WINDOW} in the sub-100\,ms zone measured in 
Section~\ref{subsubsec:precision-time-window-multi-user} is just as pronounced under real traffic, 
at approximately 56\% precision, and is therefore not a measurement artifact. 
What differs is how often that zone is reached. 
Real concurrent users produce it noticeably less frequently, in 23\% of logins, than the 
artificially dense stress case, which reaches it in 87\%. 
For operation this means that the risk is real and reproducibly demonstrated, but occurs less 
often under the observed user load than the stress case figure alone would suggest.

The contribution of \textit{ipHash} depends entirely on whether the source actually separates 
users. 
Section~\ref{subsubsec:influence-of-iphash} shows that with separate sources \textit{ipHash} alone 
separates just as well as \textit{ipHash} and \textit{usernameHash} combined, yielding identical 
candidate sets in every measured window. 
Section~\ref{subsubsec:precision-nat} shows the counterpart, namely that where several users share 
one address \textit{ipHash} contributes nothing at all, since \texttt{IP\_ONLY} and 
\texttt{TIME\_WINDOW} produce identical figures there. 
For scenarios in which \textit{usernameHash} is unavailable, this is the differentiated answer. 
The heuristic is only as good as the least discriminating identifier available to it. 
Where a shared address and a missing user identifier coincide, only \texttt{TIME\_WINDOW} remains, 
with the density dependence observed consistently throughout.

The productive strategy withstands the shared address case as long as \textit{usernameHash} 
remains available. 
This is the practically most relevant conclusion of Section~\ref{subsubsec:precision-nat}, since 
\texttt{HASH\_AND\_TIME\_WINDOW} retains 100\% precision although all three test users share one 
address. 
Only when the user identifier is absent in addition to the shared address does the correlation 
become a question of the time window alone, which reduces to the density dependence already 
established rather than constituting a new risk specific to network address translation.

\section{Detection}\label{sec:eval-detection}

This section evaluates the thirteen detection rules described in 
Section~\ref{subsec:impl-detection}. 
It first establishes what the reported figures can and cannot show, then presents the test 
coverage per rule, and finally reports three defects that the evaluation itself uncovered.

\subsection{What the Figures Represent}\label{subsec:detection-semantics}

An important qualification precedes the results. 
The figures reported here are not the outcome of a sampling study over productive traffic. 
No labelled dataset of real logins exists against which precision and recall could be computed. 
What is evaluated instead are test cases, that is scenarios constructed by the developer in which 
the expected outcome is fixed in advance.

Three terms are used throughout this section. 
A true positive proof means that a test constructs a scenario in which a rule is supposed to fire 
and the assertion confirms that it does. 
A true negative proof means that a test constructs a scenario in which no alert is supposed to be 
raised and the assertion confirms that none is. 
A false negative class is not a measured rate but a case derivable from the code in which an 
actual attack would structurally produce no alert.

The strength of a true negative proof is not uniform, and this distinction turns out to matter. 
A negative case constructed directly in Java verifies only that the rule remains silent when 
given a correctly formed input object. 
It does not verify whether the pipeline preceding the rule, comprising the Logstash parsing and 
the field mapping, produces such an object correctly in practice. 
A negative case established through a real login verifies both at once. 
Section~\ref{subsec:detection-logstash-defect} presents a case in which precisely this difference 
made a defect visible that had remained invisible otherwise.

This evaluation therefore answers whether the implemented code behaves exactly as intended for 
the constructed cases. 
It does not answer how often the system errs in operation. 
Section~\ref{sec:validity} returns to this distinction.

\subsection{Test Layers}\label{subsec:detection-layers}

The rules are verified on three layers that differ in how much of the system they exercise. 
Unit tests examine a rule in isolation with its repository replaced by a mock. 
They verify the detection logic itself and are the fastest to write and to execute.

Layer one tests run the rule against a real Elasticsearch instance provided through 
Testcontainers. 
Compared with a unit test, this additionally covers the query as it is actually formulated in the 
Elasticsearch query language, the index mapping and the serialisation of the stored documents. 
The rule under test is invoked directly rather than through the scheduler, which decouples the 
correctness of the detection from the timing of the scheduler.

Layer two tests exercise the complete path. 
A real browser performs a login against the real IdP, the resulting audit entry passes through 
Filebeat and Logstash into Elasticsearch, and the test then verifies the alert produced by the 
backend. 
This is the only layer on which a defect in the log shipping pipeline can become visible.

\subsection{A Defect Visible Only through the Full Pipeline}\label{subsec:detection-logstash-defect}

The true negative proof for \texttt{UNENCRYPTED\_ASSERTION} on layer two required a service 
provider whose assertions are actually encrypted, since the existing one transmitted them in 
plain text. 
A second provider was therefore registered with \texttt{encryptAssertions=true} and a real login 
performed against it. 
The expectation was that no alert would be raised.

The first run contradicted this. 
For the same login, Elasticsearch contained both \textit{encryption\_algo} with the value 
\texttt{AES128-GCM} and \textit{encrypted} with the value \texttt{false}, which is an internal 
contradiction since both fields originate from the same audit line.

The cause lay in the log shipping pipeline rather than in the rule. 
The audit format logs \texttt{\%XA}, the algorithm, which Logstash maps correctly. 
It does not log the separate standard token for the encryption state, which Logstash therefore 
derives from a backward compatibility alias that the audit format never populated. 
The subsequent processing logic recognises only the literal strings \texttt{true} and 
\texttt{false}, so that an empty value falls into the same branch as \texttt{false}. 
The field \textit{encrypted} was consequently set to \texttt{false} for every login, entirely 
independently of the actual encryption state.

The consequence is not a missed detection but the opposite. 
For genuinely unencrypted logins the result remained accidentally correct. 
For encrypted logins the rule would have reported every single one as 
\texttt{UNENCRYPTED\_ASSERTION}. 
This is not a rare edge case but a structurally guaranteed false positive rate of one hundred 
percent across all encrypted traffic, concealed solely by the fact that the test environment had 
until then contained no service provider with encryption enabled.

The defect was invisible on layer one for a structural reason. 
The three existing negative scenarios for this rule construct their audit object directly in Java 
with the encryption state set explicitly and therefore never pass through Logstash at all. 
A test that bypasses the pipeline cannot, in principle, find a defect located within it. 
The fix derives the encryption state from the algorithm field, treating a non-empty value as 
encrypted. 

After restarting Logstash, a login against the same service provider produced documents carrying 
\textit{encryption\_algo} with the value \texttt{AES128-GCM} and \textit{encrypted} correctly set 
to \texttt{true}.

\subsection{A Defect Visible Only against Real Persistence}\label{subsec:detection-version-defect}

A second defect illustrates why layer one is not redundant with respect to unit testing.
During development, the unit test for \texttt{BEHAVIOR\_ANOMALY} passed consistently while the 
rule did not work in operation. 
The behaviour profile of a user was written once and never updated thereafter. 
The cause was a missing version field on the stored document, which caused Elasticsearch to 
discard every update silently rather than to reject it with an error. 

A mock-based test cannot detect this class of defect. 
The mocked repository returns success for every save operation, irrespective of whether a real 
Elasticsearch instance would have accepted the document. 
The test therefore verified that the rule calls the repository, not that the repository call has 
any effect. 
This finding is the reason why layer one was introduced for all thirteen rules rather than only 
for those where it seemed most obviously necessary. 

\subsection{A Systemic Class of False Negatives}\label{subsec:detection-registry-guard}

Eight of the thirteen rules begin by checking whether the audit field they depend on is present 
in the field registry, and return without a result if it is not. 
As a design decision this is sound, since a rule should not guess when the data it requires is 
absent, as argued in Section~\ref{subsec:detection}.

The consequence, however, is that the detection coverage of the system is bounded from above by 
the completeness of the audit configuration rather than by the detection logic itself. 
An operator who shortens the audit format for reasons of data protection or storage reduces the 
detection surface accordingly, and no alert or warning indicates that this has happened. 
The rules do not fail in that case, they simply remain silent.

A related case occurred in the development environment of this work. 
Two rules depend on the service provider configuration, which reaches the backend exclusively 
through a dedicated ingest path. 
That path was inactive for an extended period, first because a security configuration no longer 
permitted the corresponding request and later because the pipeline configuration referenced an 
outdated address. 
Both rules therefore evaluated against an index that was no longer being updated, without any 
indication that their input had become stale.

\subsection{Coverage of the Documented Attack Space}\label{subsec:detection-attack-space}

The figures presented so far describe the relationship between the rules and the tests written 
for them. 
They say nothing about the relationship between the rules and the attacks that actually occur, 
since both the rules and the scenarios originate from the same source.

A partial answer is available through the assignment established in 
Section~\ref{subsec:detection}, where the rules were related to the vulnerabilities and attack 
classes documented by Simpson and Groß~\cite{FIMSurvey}. 
That assignment provides a denominator that was not defined by this work. 
Of the six cross-protocol issues concerning SAML, the implemented rules address two directly, 
while a third, namely \texttt{SIGNATURE\_WRAPPING\_SUSPECTED}, addresses the same attack class 
through a vulnerability that the survey does not list for SAML.

The remaining issues are not addressed, and the reasons are structural rather than a matter of 
implementation effort. 
They are discussed in Chapter~\ref{ch:discussion}.

\subsection{Thresholds}\label{subsec:detection-thresholds}

Several rules depend on numerical thresholds, among them the number of failed attempts and the 
length of the window within which they are counted, the number of logins before a behaviour 
profile is considered established, and the number of occurrences after which a replay is 
reported.

None of these values has been subjected to a sensitivity analysis, that is an examination of the 
threshold at which a true positive turns into a false negative. 
They were chosen as plausible point values rather than derived from measurement. 
Since the thresholds were moved into the configuration during this work, such an analysis has 
become technically possible, but it has not been carried out.

\subsection{Interpretation of the Results}\label{subsec:interpretation-detection}

All thirteen rules behave as intended for the scenarios constructed for them, and all are 
verified against real persistence rather than against mocks alone. 
This is a statement about the fidelity of the implementation, and within that scope it is a 
complete one.

It is not a statement about detection quality in operation. 
Determining how reliably a rule identifies genuine attacks would require productive traffic in 
which each login is independently labelled as malicious or benign. 
Such a dataset does not exist for this work and cannot be produced within a test environment. 
The circularity of rules and scenarios originating from the same source is therefore not resolved 
by the figures reported here, although the derivation of the rules themselves, as described in 
Section~\ref{subsec:detection}, no longer rests on the author's own judgement.

What the evaluation did establish is of a different kind. 
Three defects became visible that operation itself did not reveal. 
A missing version field caused every profile update to be discarded silently, a pipeline defect 
would have reported every encrypted login as unencrypted, and the dependence of two rules on a 
stale index went unnoticed for months. 
In all three cases the system continued to run, alerts continued to be produced and the dashboard 
continued to be populated. 
The defects became apparent only when the behaviour was measured systematically against an 
expectation defined in advance.

\section{Performance Overhead}\label{sec:overhead}

This section presents the results of the overhead evaluation of the custom interceptor. 
The interceptor runs as a \textit{postAuthenticationFlow} within the IdP and therefore lies on 
the critical path of each authentication process. 
The evaluation addresses two questions:

\begin{itemize}
      \item How much overhead does the interceptor introduce to the end-to-end authentication 
            latency?
      \item Does the difference between asynchronous and synchronous transmission justify the 
            use of fire-and-forget transmission?
\end{itemize}

To measure the overhead introduced by the interceptor, three different configuration modes are 
evaluated: \textit{baseline}, \textit{async}, and \textit{sync}. 
In the \textit{baseline} configuration, no \textit{postAuthenticationFlow} is configured for the 
SP. 
The custom interceptor is therefore not executed during the authentication process. 
In the \textit{async} configuration, the \textit{postAuthenticationFlow} is enabled for the SP 
and the custom interceptor is executed. 
The interceptor transmits the collected data to the monitoring tool without waiting for a 
response. 
The transmission therefore follows a fire-and-forget approach. 
The \textit{sync} configuration also executes the custom interceptor for the SP, but the 
interceptor waits for a response from the monitoring tool before completing its execution. 
It therefore verifies whether the transmitted payload was received successfully.

Comparing \textit{baseline} against \textit{async} quantifies the cost of the interceptor in its 
productive configuration. 
Comparing \textit{async} against \textit{sync} quantifies the cost of the design decision 
described in Section~\ref{sec:impl-transport}, namely what waiting for a confirmation would cost 
if the records were transmitted synchronously.

\subsection{Measurement Sources}\label{subsec:measurement-sources}

The overhead is evaluated using three measurements that differ in what they include.
The \textit{internal} measurement is obtained through the \textit{executionTimeMs} 
instrumentation within the interceptor. 
It measures the time required for data collection, hashing, and XML extraction performed by the 
action. 
This represents a lower bound, because payload construction and data transmission are excluded. 
The measured value is included in the generated payload and is therefore available for every 
login without additional instrumentation.

The \textit{external} measurement records the end-to-end duration of a login as observed by the 
client. 
It includes everything the user experiences, from the initial request to the point at which the 
SP grants access, and therefore covers the interceptor together with all other processing steps 
of the IdP. 
This is the measurement that answers whether the overhead is perceptible in practice.

The \textit{CPU} measurement records the processor utilisation of the IdP container during a run 
via \texttt{docker stats}. 
It serves as an independent confirmation, since the two latency measurements could in principle 
fail to detect an effect that manifests itself as additional computation rather than as 
additional waiting time.

\subsection{Experimental Design}\label{subsec:experimental-design}

The experiment comprises six runs, each executing all three configurations in sequence, which 
results in eighteen measurements in total. 
Each run performs one hundred logins per configuration.
The order of the configurations is rotated between runs so that each configuration occupies each 
of the three positions exactly twice:

Without rotation, a configuration measured consistently in the last position would appear slower

The experimental unit is the run, not the individual login. 
The one hundred logins within a run share the same JVM state, the same container and the same 
system load, and are therefore pseudo-replicates rather than independent observations. 
Treating them as independent would suggest a precision that the experiment does not provide, 
since the dominant source of variation lies between runs rather than within them. 
Each run consequently contributes a single value per configuration, namely the median of its one 
hundred logins, which yields eighteen observations for the analysis.

Before each measurement run, a single test login verifies that the configuration under test is 
actually active. 
The verification queries the monitoring backend and checks whether the login produced an 
interceptor report, expecting none for \textit{baseline} and one for the other two 
configurations. 
This gate was introduced after an earlier series had to be discarded, in which the backend had 
not been reachable and all three configurations had therefore been measured under effectively 
identical conditions.

\subsection{Resolution of the Measurement Environment}\label{subsec:measurement-resolution}

The discarded preliminary series, in which the backend had not been reachable, provides an 
empirical measure of the noise floor. 
Since all three configurations were effectively identical under that condition, its twelve runs 
constitute twelve repetitions of the same measurement. 
They yield a mean of 324,6\,ms with a standard deviation of 18,1\,ms and a span of 51\,ms.

This quantifies, independently of the actual measurement series, which effect sizes the 
environment is able to resolve at all. 
It also agrees with the between-run variation observed in the valid series, which lies between 16 
and 23\,ms.

\subsection{Correction of the Analysis Script}\label{subsec:script-correction}

The figures reported above differ slightly from an earlier version of this analysis. 
The evaluation script contained two indexing errors, among them a missing final measurement row 
per run during the computation of the means. 
Both were corrected, and the values presented here reflect the corrected computation.

The errors are worth reporting because they were not visible in the output. 
The script produced plausible figures in both cases, and the discrepancy only became apparent 
when individual values were traced back to the raw measurement files. 
This mirrors the pattern observed in the correlation evaluation, where a defect likewise 
manifested itself not as an error but as a result that appeared correct.

\subsection{Interpretation of the Results}\label{subsec:interpretation-overhead}

The asynchronous interceptor introduces no measurable overhead. 
The point estimate lies at $-1,6$\,ms and the upper bound of the confidence interval at 
approximately 28\,ms, which is below nine percent of the login duration. 
The internal measurement reports 0,90\,ms for the work performed within the action. 
Both sources support the same conclusion, namely that the overhead is not perceptible to users.

That the external benchmark shows no effect is not a weakness of the measurement but a 
consequence of the magnitudes involved. 
An effect of one millisecond cannot become visible in a measurement of 320\,ms with a 
between-run spread of roughly 20\,ms, irrespective of how carefully the experiment is conducted.

The synchronous mode tends to be slower, but this is not statistically established. 
The point estimate places \textit{sync} between 24 and 26\,ms above the other two configurations, 
which is plausibly explained by the blocking HTTP round trip to the backend, including the 
Elasticsearch write and the correlation attempt, within the critical path. 
The direction is consistent across runs, yet with six runs per configuration the confidence 
intervals do not exclude zero. 
This is a clear indication rather than a confirmation.

For the design decision described in Section~\ref{sec:impl-transport}, the argument nevertheless 
points in the same direction. 
Even the point estimate for an additional synchronous round trip lies in the low tens of 
milliseconds rather than in the hundreds. 
A firmer statistical foundation would require a larger number of runs, which is discussed in 
Section~\ref{sec:validity}.
