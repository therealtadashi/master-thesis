\chapter{Evaluation}\label{ch:evaluation}

This chapter evaluates the proposed monitoring system. 
It presents the test setup, evaluates the correlation and detection capabilities, 
measures the performance overhead introduced by the interceptors, lists the defects that the 
evaluation uncovered, and concludes with a discussion of the threats to validity.

\section{Test Setup}\label{sec:setup}

To facilitate integration with the Java testing framework, the test environment runs in containers. 
This comprises the Shibboleth IdP, an LDAP directory serving as the user store, the SPs and the 
log shipping stack. 
Only the backend application of the monitoring tool and the test code run directly on the host. 

Two SPs are deployed, referred to as the weak SP and the clean SP in the following. 
The weak SP is used for the detection scenarios and is configured to exhibit the weaknesses
that the rules are intended to identify. 
The clean SP is configured according to current recommendations and serves as a reference for
the false positive rate, since any alert raised for a legitimate login against it is by
definition a false positive. 

The evaluation distinguishes three levels of testing. 
Unit tests examine individual components in isolation, with their dependencies replaced by
mocks, so that a test result reflects the behaviour of that component alone. 
Integration tests run against a real Elasticsearch instance, which additionally covers the
persistence layer, the index mappings and the queries that a mock cannot represent. 
End-to-end tests exercise the complete pipeline, from a login at the SP through the log
shipping stack to the alert produced by the backend. 

Logins are generated in two ways. 
An HTTP client harness performs the SAML login sequence directly, parsing the forms returned
by the IdP and submitting them without rendering the pages. 
Selenium based tests drive an actual browser through the same sequence. 
The two differ in the interval between consecutive logins, since the harness proceeds as fast 
as the server responds whereas a browser adds the time required for page loading and form 
interaction.
This difference is relevant for the correlation measurements in Section~\ref{sec:eval-correlation},
where the temporal density of logins determines how reliably records can be matched. 

The environment is not a production deployment. 
It comprises a single IdP, two SPs and a small number of test accounts, and all traffic is generated 
for the purpose of measurement. 
The implications of this are discussed in Section~\ref{sec:validity}.

\section{Correlation}\label{sec:eval-correlation}

Section~\ref{subsec:impl-correlation} described the correlation mechanism, which links each 
post authentication report to the audit entry of the same login. 
It first tries \texttt{INBOUND\_\allowbreak{}MESSAGE\_\allowbreak{}ID} and falls back to two 
heuristic strategies where the identifier is not available. 
Both heuristics query the audit entries of the same SP within a time window around the report. 
\texttt{HASH\_\allowbreak{}AND\_\allowbreak{}TIME\_\allowbreak{}WINDOW} additionally requires the 
same \textit{usernameHash} and \textit{ipHash}, whereas \texttt{TIME\_\allowbreak{}WINDOW} relies 
on the time alone. 
The entries returned by such a query are referred to as candidates in the following, and the 
strategy selects the candidate with the smallest temporal distance to the report. 
This section examines how often the selected candidate is the correct one (precision) and how 
many reports find a counterpart at all (coverage). 
The exact strategy serves as the reference for the heuristics, and the measurement is repeated on 
datasets that differ in the number of users and in the login generator. 

\subsection{Method and Datasets}\label{subsec:eval-correlation-method}

\paragraph{Ground truth.}
To determine the precision of the heuristic strategies, a reference is required that indicates 
whether a given correlation was correct. 
The correlation via \texttt{INBOUND\_\allowbreak{}MESSAGE\_\allowbreak{}ID} establishes a 
one-to-one relationship, since the identifier is unique per request. 
Wherever this strategy produced a match, the correct counterpart is therefore known without 
ambiguity, which allows it to serve as a ground truth for the heuristic strategies. 
An analysis program in the test sources of the backend proceeds as follows:

\begin{itemize}
    \item It collects all post authentication reports of a configurable time period that were correlated via \texttt{INBOUND\_\allowbreak{}MESSAGE\_\allowbreak{}ID}.
    \item For each report and each window size from $\pm$1 to $\pm$60\,s, it executes the query of the heuristic strategy unchanged and selects the same candidate as the productive system would, namely the one with the smallest temporal distance.
    \item It compares the selected candidate with the known correct audit entry and classifies the outcome as a hit, an incorrect assignment or no match. Precision is the share of hits among the assigned reports, coverage the share of reports that were assigned at all.
    \item It records the offset between the reception of the report and the event time of its audit entry, and the distance to the nearest other audit entry of the same SP as a measure of the local login density.
\end{itemize}

In operation, an audit entry that has already been assigned to a report is no longer offered as a 
candidate for other reports. 
The analysis has to omit this filter, since every audit entry in the ground truth has already been 
assigned to its correct report, so that the filter would remove exactly the candidate that is being 
looked for. 
Each report is therefore evaluated against all audit entries in its window.

\paragraph{Datasets.}
The heuristics only take effect when the audit log lacks the inbound message identifier, for 
instance because an operator does not record it or uses an older audit format. 
Whether they then select the correct entry depends on two properties of the traffic: how many 
logins at the same SP fall into the same time window, and whether these logins can be told apart 
by subject and address. 
Both vary considerably in operation. 
At the start of a lecture or during an exam registration, many users log in at the same SP within 
a few seconds, while at night a single login may stand alone. 
Some users log in from an address of their own, while others share one behind a gateway. 
The five datasets reproduce these situations step by step, each adding a condition that the 
previous ones leave open. 
Table~\ref{tab:correlation-datasets} summarises how they were generated. 
Coverage is additionally determined on the performance series of Section~\ref{sec:overhead}, 
which comprises 7{,}236 reports and is by far the largest dataset. 

The starting point is the simplest case, a single user who logs in repeatedly at the same SP (D1). 
For the heuristics, this case removes every distinguishing feature except time. 
All candidates share subject, address and SP, so that the hashes exclude nothing and both 
heuristics behave like \texttt{TIME\_\allowbreak{}WINDOW}. 
The correct entry can only be found if the time recorded for each login is precise enough to keep 
consecutive logins apart. 
D1 therefore tests the time base on which both heuristics rest. 
If it failed here, none of the further scenarios could succeed. 

In operation, however, the logins within a window rarely stem from one person. 
In D2, three users log in at the same SP at the same time, so that candidates of different users 
lie in the same window. 
This is precisely the situation for which the hashes exist. 
\texttt{HASH\_\allowbreak{}AND\_\allowbreak{}TIME\_\allowbreak{}WINDOW} can discard the entries of 
other users, whereas \texttt{TIME\_\allowbreak{}WINDOW} has to choose among all of them by time 
alone. 
D2 is thus the first dataset in which the two heuristics differ, and it shows what an operator 
loses who records neither the subject nor the address in the audit log. 

D1 and D2 are generated by the HTTP harness, which starts the next login as soon as the server has 
answered. 
It produces logins at intervals that no user reaches with a browser, since loading pages and 
filling in forms take time. 
If the harness is considerably denser than real traffic, D2 overstates how often the time alone 
fails. 
D3 therefore repeats D1 with Chrome driven by Selenium, which loads every page and submits the 
forms as a browser does, and shows how closely spaced the logins of one user are under real 
browser timing.

D3 still covers only one user. 
D4 combines the two previous steps: three users log in simultaneously, each through its own 
browser, which comes closest to several people logging in at the same time. 
It shows whether the weakness of \texttt{TIME\_\allowbreak{}WINDOW} that D2 exposes also occurs 
under browser timing, and how often. 
Since every browser runs in its own container, each user also has an address of their own, as 
users at different devices or in different networks do. 
This makes it possible to analyse the same data a second time without \textit{usernameHash} and 
to determine whether \textit{ipHash} alone keeps the users apart.

Separate addresses cannot be taken for granted, however. 
Behind a gateway with network address translation, for instance in a company network, a dormitory 
or a public wireless network, many users appear under the same address, and \textit{ipHash} no 
longer distinguishes them. 
The separation then rests on \textit{usernameHash} alone. 
D5 reproduces this case by running three users as threads of a single process, so that all logins 
originate from one address.

\paragraph{Every report finds its counterpart.}
In the performance series, all 7{,}236 post authentication reports were correlated with their 
audit entry through the inbound message identifier, and none expired without a counterpart. 
The coverage of the exact strategy was therefore 100 percent, with a lower bound of 99.95 percent 
for the 95 percent Wilson interval~\cite{Wilson}. 
That this figure can be determined at all is due to the sweep described in 
Section~\ref{subsec:impl-correlation}, which marks reports without a counterpart as permanently 
uncorrelated after a waiting period, so that a lost report can be told apart from one that is still 
waiting. 
The heuristics, too, assigned every report in all five datasets, even with the smallest window of $\pm$1\,s. 
This follows from the offsets in Table~\ref{tab:correlation-offset}: a report arrives at most about 
160\,ms before or after the event time of its audit entry, so that the correct entry always lies 
within the window. 
Where a heuristic fails, it therefore assigns a report to the wrong counterpart rather than to none, 
which is why the following paragraphs concern precision.

\paragraph{With the hashes, the heuristic is as reliable as the exact strategy.}
\texttt{HASH\_\allowbreak{}AND\_\allowbreak{}TIME\_\allowbreak{}WINDOW} selected the correct entry 
for every report in all five datasets. 
This includes D1, where the hashes exclude nothing and the event time alone decides, and D5, where 
all users share one address. 
The size of the window does not affect the precision. 
In D1 the mean number of candidates rises from 6.4 at $\pm$1\,s to 197.6 at $\pm$60\,s without a 
single wrong assignment, since a larger window only adds candidates that lie further away and are 
therefore never selected. 
The window therefore only has to be large enough to contain the correct entry, and a larger window 
costs nothing but query effort. 
In the test environment $\pm$1\,s would have sufficed, but in operation a report can arrive later, 
since the interceptors give up a transmission only after 1.5\,s, and on separate hosts the clocks 
may differ. 
The default of $\pm$10\,s covers both with a wide margin, at the price of examining 58.1 instead of 
6.4 candidates per report in D1. 

\paragraph{Without the hashes, wrong assignments occur only between logins less than 100\,ms apart.}
\texttt{TIME\_\allowbreak{}WINDOW} reached 65.0 percent in D2, 73.7 percent in D5 and 89.9 percent 
in D4. 
Table~\ref{tab:correlation-density} breaks these figures down by the distance of each login to the 
nearest other login at the same SP, with the number of logins in each range in parentheses. 
All wrong assignments concern logins with a distance below 100\,ms. 
At larger distances, \texttt{TIME\_\allowbreak{}WINDOW} was correct in every case. 
Within this zone, it selected the correct entry in 56 to 69 percent of cases, regardless of whether 
the logins came from the harness or from browsers. 
The differences between the overall figures therefore do not stem from the strategy but from how 
many logins fall into the zone: 87 percent in D2, 84 percent in D5 and 23 percent in D4.

\paragraph{Real browser traffic reaches this zone far less often.}
With a single browser user (D3), every login lay more than one second away from the next, and a 
window of $\pm$1\,s contained on average one candidate instead of 6.4 with the harness. 
Even with three users logging in simultaneously through browsers (D4), less than a quarter of the 
logins fell below 100\,ms. 
The weakness of \texttt{TIME\_\allowbreak{}WINDOW} is thus not an artefact of the harness, since it 
is just as pronounced within the zone, but the harness reaches the zone far more often than browser 
traffic does. 
How often a productive IdP reaches it depends on its load at peak times and cannot be derived from 
the test environment.

\paragraph{Each hash covers the case in which the other one is uninformative.}
In D4, every user had an address of their own. 
Analysed without \textit{usernameHash}, the heuristic found exactly the same candidates as with both 
hashes, for every window size and including the 138 logins below 100\,ms, and thus again reached 
100 percent. 
\textit{ipHash} alone therefore separates users who log in from different devices or networks. 
In D5, where all users shared one address, the same variant produced exactly the figures of 
\texttt{TIME\_\allowbreak{}WINDOW}, since a filter on the only address present excludes nothing. 
\texttt{HASH\_\allowbreak{}AND\_\allowbreak{}TIME\_\allowbreak{}WINDOW} nevertheless remained at 
100 percent, because \textit{usernameHash} separated the users on its own. 
In all tested scenarios, the heuristic thus stays exact as long as at least one of the two 
identifiers distinguishes the users, and it falls back to the density dependence of 
\texttt{TIME\_\allowbreak{}WINDOW} only when both are missing or uninformative.

\paragraph{Operating limit of the heuristics.}
Table~\ref{tab:correlation-offset} shows the offset between the reception of a report and the event 
time of its audit entry. 
This was not recorded for D2. 
It is mostly negative, by about 30\,ms, because the post authentication interceptor runs in the 
middle of the profile flow, whereas \texttt{\%T} marks the completion of the transaction. 
Since the heuristics select the entry closest to the reception time, a neighbouring login can only 
be selected instead of the correct one if the two lie closer together than twice the largest 
absolute offset (last column). 
Across all datasets, this critical distance is at most 316\,ms (D4), which corresponds to about 
three logins per second. 
For \texttt{HASH\_\allowbreak{}AND\_\allowbreak{}TIME\_\allowbreak{}WINDOW}, the limit applies to 
logins of the same subject from the same address at the same SP, a rate that interactive users do 
not reach. 
For \texttt{TIME\_\allowbreak{}WINDOW}, it applies to all logins at an SP, which explains why this 
strategy fails in dense traffic. 
The bound is conservative, since wrong assignments were only observed below 100\,ms. 
All offsets were measured on a single host, where the IdP and the backend share one clock. 
On separate hosts, the difference between the clocks adds to the offset and lowers the limit, so 
that the offset, which the analysis records, has to be measured again in a different environment.

Taken together, the correlation found a counterpart for every report, and with the inbound message 
identifier or at least one separating hash, it found the correct one in every tested scenario. 
Only an audit log that records neither the identifier nor the hashes leaves the correlation to time 
alone, and it then assigns reports to the wrong entry where logins at the same SP follow each other 
within less than 100\,ms. 
Operators should therefore record \texttt{\%I} in the audit format or, where that is not possible, 
at least the subject and the address.

\section{Detection}\label{sec:eval-detection}

Section~\ref{subsec:impl-detection} described the detection layer, which evaluates fifteen rules 
in four engines, one for each type of input: the login events derived from the audit log, the 
configuration of an SP, its metadata, and the post authentication reports. 
Most rules examine a single input for a condition that indicates a weakness or an attack, for 
instance an assertion that was sent unencrypted or a series of failed logins for the same subject. 
Two rules compare records that were produced independently of each other. 
The consistency check compares the outbound report with the audit entry of the same login and 
raises \texttt{FIELD\_\allowbreak{}MISMATCH} when the two disagree, and 
\texttt{CORRELATION\_\allowbreak{}DISCREPANCY} reports a post authentication report for which no 
audit entry arrives within the waiting period.

This section examines whether each rule behaves as specified, that is whether it raises an alert 
when the condition it examines occurs and remains silent when it does not. 
Since no productive logins with a known classification are available, the rules are tested in 
scenarios whose expected outcome is fixed in advance, on the test levels introduced in 
Section~\ref{sec:setup}, and series of legitimate logins show whether alerts arise where none are 
due.

\subsection{Method and Scenarios}\label{subsec:eval-detection-method}

\paragraph{Proofs.}
The tests establish two kinds of proof. 
A true positive proof constructs a scenario in which a rule is supposed to raise an alert and 
confirms that it does. 
A true negative proof constructs a scenario in which no alert is due and confirms that none is 
raised. 
How much a proof shows depends on the test level at which it is established. 
In an integration test, the test builds the input of the rule itself, for instance an audit entry 
or a post authentication report, stores any history the rule requires in Elasticsearch and passes 
the input directly to the rule engine rather than waiting for the scheduler, so that the result does 
not depend on its timing. 
Such a proof covers the rule, its queries and the stored documents, but not the way in which 
Filebeat and Logstash turn a real audit line into such an input. 
An end-to-end test starts from a real login in the browser and covers this path as well, which 
makes it the only level at which a fault in the log shipping stack can become visible.

\paragraph{Scenarios.}
In operation, the detection layer has to meet two expectations at once. 
It has to report the weaknesses and attacks that the rules describe, and it has to remain quiet 
during the vast majority of logins, which are legitimate, since an operator who receives alerts for 
ordinary logins soon stops reading them. 
The two comparison rules carry a third expectation, namely to notice when a record has been altered 
or has gone missing. 
The scenarios address these expectations in turn and finally repeat the second one under sustained 
load.

Every rule has at least one scenario at the integration level that contains the condition it is 
meant to detect. 
For most rules this is a single prepared input, such as an audit entry that records an unencrypted 
assertion or a SAML request with two signature elements, a typical trace of a signature wrapping 
attack, which the rule treats as a possible signature wrapping attempt. 
Rules that depend on history receive it in the same way. 
For \texttt{BEHAVIOUR\_\allowbreak{}ANOMALY} the test first stores five logins of a user from a known 
address and then one from a new address, and for \texttt{CORRELATION\_\allowbreak{}DISCREPANCY} it 
stores a post authentication report that arrived twenty minutes earlier, so that the waiting period 
of fifteen minutes has already elapsed. 
Wherever a regular login in the test environment can produce the condition, an end-to-end scenario 
follows: a login with the user agent of a script, a login with a wrong password, five failed logins 
in quick succession, which exceeds the threshold of three within five minutes, and a login at the 
weak SP, whose assertions are not encrypted. 
For the remaining rules, an end-to-end scenario would require more than a regular login, for 
instance a second browser with another address, an SP that offers an MFA flow, a crafted or 
replayed message, a changed configuration or metadata of an SP, or log shipping that stays 
interrupted for longer than the waiting period. 
These scenarios were not implemented in this work. 
Table~\ref{tab:detection-coverage} names the requirement for each rule. 

The second expectation is tested with legitimate logins through the browser. 
At the clean SP, three users log in alternately, 100 times in total, and after a further 
100 seconds, in which the scheduler evaluates all entries, none of the logins may have raised an alert. 
Since every alert in this run would be a false alarm, the run is at the same time a true negative 
proof for every rule that can react to a login. 
The same run against the weak SP tests the consistency check in the presence of the alerts that the 
weaknesses of this SP rightly cause, so that there no \texttt{FIELD\_\allowbreak{}MISMATCH} alert may 
arise. 
In addition, a single legitimate login at the clean SP provides the end-to-end true negative proofs of 
the five rules marked TN in Table~\ref{tab:detection-coverage}. 

The third expectation concerns someone who alters the audit entry of a login after the fact, for 
instance to conceal which request a response answered. 
The consistency check is meant to notice this, since the outbound report is produced 
independently by the IdP and reaches the backend directly. 
It compares the fields that both records contain and that the audit format records. 
For every login these are the status, the identifier of the request answered by the response, the 
identifier and the issue time of the outbound message and the encryption state. 
For an unencrypted assertion, the identifier of the assertion, the authentication instant, the authentication 
context, the format of the name identifier and the pseudonymised name identifier are compared as well. 
To produce a manipulation, a login against the clean SP was performed while the backend was 
stopped. 
After the audit entry had reached Elasticsearch, the identifier of the answered request was 
replaced by a different value, and the backend was started again.

Finally, the comparison rules must not raise false alarms when many logins arrive in quick 
succession, since both rely on the records of every login being matched in time. 
The performance series of Section~\ref{sec:overhead} provides this load with 10{,}854 logins 
against the weak SP, in measurements of about 200 logins each. 
In 7{,}236 of them the interceptors were active and transmitted both reports. 
The remaining logins belong to the baseline configuration without interceptors.

\paragraph{Every rule is proven against a real Elasticsearch instance, and six are also tested end-to-end.} 
All fifteen rules have a true positive proof on the unit and on the integration level, so that for 
every rule the queries, the index mapping and the stored documents are covered and not only the 
detection logic. 
The test suite comprises 118 unit tests for the rules, 21 integration tests and seven end-to-end 
tests. 
Six rules are additionally proven from a real login. 
For \texttt{SUSPICIOUS\_\allowbreak{}USER\_\allowbreak{}AGENT}, \texttt{FAILED\_\allowbreak{}LOGIN}, 
\texttt{BRUTE\_\allowbreak{}FORCE} and \texttt{UNENCRYPTED\_\allowbreak{}ASSERTION}, the end-to-end 
level contains both a true positive and a true negative proof. 
\texttt{WEAK\_\allowbreak{}ENCRYPTION} has only the true negative proof, since no SP in the test 
environment requests a weak algorithm, and the true positive proof of 
\texttt{FIELD\_\allowbreak{}MISMATCH} is the manipulation described below. 
For the remaining nine rules, the last column of the table names what an end-to-end scenario would require. 
That the end-to-end level is not redundant became apparent when it uncovered a fault in the log 
shipping stack that no integration test could have found (Section~\ref{sec:defects}).

\paragraph{Legitimate logins raise no false alarms.}
In the 100 logins at the clean SP, none of the logins raised an alert, and in the 100 logins at the 
weak SP, where the alerts caused by its weaknesses are expected, no 
\texttt{FIELD\_\allowbreak{}MISMATCH} was raised. 
In all 200 logins, the post authentication report was correlated with its audit entry through the 
inbound message identifier, and the consistency check passed, with five compared fields at the 
clean SP and ten at the weak SP (Table~\ref{tab:consistency-fp}). 
No false alarm in 100 logins does not prove that false alarms cannot occur, but it makes a rate 
above 3.7 percent per SP unlikely, with 95 percent confidence according to the Wilson 
interval~\cite{Wilson}. 
For both SPs together, the limit is 1.9 percent. 
At the clean SP this applies to every alert that a login can trigger, at the weak SP to the 
consistency check.
Findings about the configuration of an SP are not triggered by logins. 
The clean SP, for instance, receives a \texttt{MISSING\_\allowbreak{}MFA} alert once per day, since it 
does not offer an MFA flow. 
Sustained load did not change this. 
During the 10{,}854 logins of the performance series, the detection layer raised 21{,}712 alerts, 
all of them expected: one \texttt{UNENCRYPTED\_\allowbreak{}ASSERTION} and one 
\texttt{SUSPICIOUS\_\allowbreak{}USER\_\allowbreak{}AGENT} alert per login, since the benchmark 
addresses the weak SP and is not a browser, and four configuration alerts. 
Since these two rules report every affected login rather than the condition once, a persistent 
weakness of an SP produces one alert per login. 
None of the alerts was a \texttt{FIELD\_\allowbreak{}MISMATCH} or 
\texttt{CORRELATION\_\allowbreak{}DISCREPANCY} alert, although the 7{,}236 logins with active 
interceptors passed through the consistency check. 
None was a \texttt{FIELD\_\allowbreak{}MISMATCH} or \texttt{CORRELATION\_\allowbreak{}DISCREPANCY} 
alert, although 7{,}236 logins of the series passed through the consistency check. 
These figures apply to the two SP configurations and to the login flow of the test environment. 
Legitimate but unusual configurations were not tested.

\paragraph{The comparison rules detect an altered or a missing record.} 
In the manipulation scenario, the backend matched the post authentication report to the altered 
audit entry through the unchanged inbound message identifier within two seconds of its start. 
The consistency check then raised a \texttt{FIELD\_\allowbreak{}MISMATCH} alert of high severity 
that named exactly the altered field and no other. 
The check thus detects a contradiction between two independently produced records of the same 
login. 
Since only one field of a single entry was altered, the test shows that the mechanism works, not how 
reliably it detects manipulations in general. 
A manipulation can only become visible in the fields that the check compares, and the check 
establishes that the two records disagree, not which of them was altered. 
For \texttt{CORRELATION\_\allowbreak{}DISCREPANCY}, the integration test confirms that a report 
without a counterpart is marked as expired after the waiting period and raises the alert. 
An audit entry that arrives only afterwards, for instance because of a delay in the log shipping 
stack, is no longer correlated, so that the alert remains although the record exists. 

\paragraph{The results establish the fidelity of the implementation, not its detection quality in operation.}
The rules were derived from documented weaknesses and requirements (Section~\ref{sec:rules}), and 
the scenarios reproduce the conditions that the rules describe. 
The results therefore show that the implementation behaves as specified: every rule raises its 
alert when its condition occurs, and legitimate logins remain without false alarms. 
How often the rules detect real attacks in operation, and how many of their alerts would be false 
for productive traffic with its unusual but legitimate configurations, cannot be derived from them. 
That would require productive logins labelled as legitimate or malicious independently of the 
rules, which no test environment can produce.

\section{Performance Overhead}\label{sec:overhead}
 
The two interceptors run inside the IdP, the post authentication interceptor as a 
\textit{post\allowbreak{}Authentication\allowbreak{}Flow} and the outbound interceptor as an 
\textit{outbound\allowbreak{}Interceptor\allowbreak{}Flow}. 
Both therefore lie on the critical path of every login, so that any time they take is added to the 
time a user waits for access to the SP, and any processor time they use is taken from the IdP. 
The evaluation addresses two questions. 
The first is how much the interceptors add to a login, in latency and in processor time, in the 
configuration intended for operation. 
The second concerns the way in which they transmit their records. 
As described in Section~\ref{sec:impl-transport}, they send them without waiting for a response, 
so that a login does not depend on the backend. 
A failed transmission is only recorded in the log of the IdP, and the record is not sent again. 
Waiting for a confirmation would allow the login to react to such a failure, and the second 
question is what waiting would cost and whether the choice of fire and forget transmission is 
justified.

Three configurations are compared. 
In \textit{baseline}, neither interceptor is configured for the SP, so that a login runs as in an 
IdP without monitoring. 
In \textit{async}, both interceptors are active and transmit their records without waiting, which 
is the configuration intended for operation. 
In \textit{sync}, both are active but wait for the confirmation of the backend, so that every login 
contains two blocking transmissions. 
The comparison of \textit{baseline} and \textit{async} answers the first question, and the 
comparison of \textit{async} and \textit{sync} the second. 
Both are measured as the client experiences a login and as processor load of the IdP, in repeated 
runs that compare all three configurations under the same conditions. 

\subsection{Method and Measurements}\label{subsec:eval-overhead-method}\label{subsec:experimental-design}

\paragraph{Measurements.}
Three measurements capture the cost of the interceptors from different angles. 
The internal measurement is recorded by each interceptor itself (\textit{executionTimeMs}) and 
covers the collection of the data, the hashing and the extraction of fields. 
It excludes the construction of the payload and the transmission and is therefore a lower bound. 
Since the value is part of every report, it is available without further instrumentation. 
The external measurement is the duration of a login as the client observes it, from the first 
request to the point at which the SP grants access. 
Since it includes every step of the login, it shows the delay that a user actually experiences. 
The third measurement records the processor utilisation of the IdP container about every two 
seconds through \texttt{docker stats}, where 100 percent corresponds to one fully used core. 
Only the samples taken during the measured logins are evaluated, so that the warm-up, in which class 
loading and compilation in the freshly started IdP raise the utilisation, is excluded. 
This measurement captures a cost that appears as additional computation rather than as additional 
waiting time, which the two latency measurements could miss. 
Since the configurations do not complete the same number of logins per second, the processor time 
per login is derived by dividing the mean utilisation by the throughput. 
The mean is used here because, unlike the median, it adds up to the total processor time of a 
measurement.

\paragraph{Procedure.}
All logins are generated by the HTTP harness for a single test account against the weak SP. 
This is the less favourable case for the interceptors, since the outbound interceptor evaluates all 
fields of the unencrypted assertion and a login of the baseline is cheaper without encryption, so 
that the relative overhead turns out larger rather than smaller. 
Each login uses a fresh client with an empty cookie store, so that it passes through the complete 
authentication without reusing a session, and the next login starts as soon as the previous one has 
completed. 
The series comprises 18 runs, each of which measures all three configurations, which yields 54 
measurements. 
For every measurement, the IdP container is recreated with the settings of the configuration, and 
a single check login verifies that the configuration is in effect by testing whether the expected 
reports arrive at the backend. 
One hundred warm-up logins follow, whose values are discarded, and then the one hundred logins that 
are measured. 
The backend runs during all measurements, including the baseline, so that the environment is the 
same, and a pause of four minutes after each measurement gives it time to process the records. 
The whole series took about five hours and comprised 10{,}854 logins.

Within a session, later measurements tended to be slower than earlier ones. 
In this series, the third position of a run was on average about 10\,ms slower than the first, 
which is of the same order as the effects to be measured, although the difference is not 
statistically established. 
Plausible causes are the memory use of the host, with about 12 of the 15\,GiB in use during the 
series, and the frequency scaling of the notebook processor. 
Neither was examined further. 
As a precaution against attributing such a drift to a configuration, the order of the 
configurations is rotated between runs, so that each configuration occupies each of the three 
positions six times. 

\paragraph{Analysis.}
The run, not the individual login, is the unit of the analysis. 
The hundred logins of a measurement share the same JVM, the same container and the same load, so 
that they are not independent observations. 
The medians of different runs differ considerably more than the scatter of the logins within a run 
would suggest, so that treating the logins as independent would overstate the precision.
Each measurement therefore contributes the median of its hundred logins and its processor time per 
login, which yields 18 values per configuration. 
The slower logins are described by the 90th percentile of each measurement. 
The differences between the configurations are estimated with a linear model that accounts for 
the run and the position within the run besides the configuration, and they are reported with their 
95 percent confidence interval. 
As a simple check, the number of runs in which one configuration was slower than the other is 
counted as well. 
With 18 runs, the confidence intervals of the latency differences have a half width of about 
11\,ms, so that smaller differences cannot be distinguished from zero.

to the two questions.

\paragraph{The work inside the interceptors takes less than half a millisecond.}
The internal measurement yields a median of 0.415\,ms for the post authentication interceptor and 
0.039\,ms for the outbound interceptor, and 99 percent of the reports stay below 2\,ms.  
Together this is about 0.45\,ms, or 0.13 percent of a median login in the baseline. 
Since the measurement excludes the construction of the payload and the transmission, it is a lower 
bound, but it shows that collecting and pseudonymising the data does not weigh on the login. 
Any larger difference between the configurations must therefore stem from building and sending the reports. 

\paragraph{Asynchronous transmission adds no latency that the experiment can distinguish from zero.}
A median login takes 6.2\,ms longer than in the baseline, and the 95 percent confidence interval 
ranges from $-4.7$ to $+17.1$\,ms and thus includes zero. 
In twelve of the 18 runs the asynchronous configuration was the slower one, which is a weak 
tendency but not an established effect. 
The slower logins behave in the same way, with a difference of 8.1\,ms at the 90th percentile and 
an upper bound of 22\,ms, or 5.2 percent. 
With 95 percent confidence, the overhead therefore lies below 17.1\,ms, or 4.8 percent of a median 
login. 
Smaller effects, such as the point estimate suggests, are below the resolution of the experiment.

\paragraph{Synchronous transmission adds about 60 milliseconds to every login.}
A median login takes 59.6\,ms or 16.7 percent longer than in the baseline, with a 95 percent 
confidence interval from $+48.7$ to $+70.4$\,ms, and the synchronous configuration was the slower 
one in all 18 runs. 
Compared with the asynchronous configuration, the difference is 53.4\,ms. 
Since every login contains two blocking transmissions, each of them costs roughly 27 to 30\,ms. 
The slower logins are affected more strongly, as the difference grows to 92.0\,ms or 21.6 percent at 
the 90th percentile. 
Since both configurations build and send the same reports, this difference is the time spent 
waiting, during which the backend validates each report and stores it in Elasticsearch before it 
answers. 

\paragraph{Asynchronous transmission costs processor time, and waiting does not save it.}
In the asynchronous configuration, the IdP spends 28\,ms more processor time on a login than in the 
baseline, with a 95 percent confidence interval from 19 to 37\,ms. 
This is 22 percent of the 126\,ms that a login costs without interceptors. 
The synchronous configuration shows a lower utilisation than the asynchronous one because it 
completes fewer logins per second, 2.36 instead of 2.71, since each login waits for the backend. 
Per login, however, it does not use less processor time than the asynchronous configuration. 
The additional processor time does not show in the latency of the asynchronous configuration because 
the transmission runs in background threads. 
At the load of the test it occupies less than half a percent of the 16 cores of the host, but it 
grows with the number of logins, so that 50 logins per second at a peak would require about 1.4 
additional cores.

In the configuration intended for operation, the interceptors therefore add no measurable latency 
and about 28\,ms of processor time to a login, which answers the first question. 
Waiting for a confirmation would add about 60\,ms to every login and more to the slow ones, without 
saving processor time. 
In the current implementation it would not even improve the delivery, since both modes only log a 
failed transmission and neither sends the record again. 
A delivery guarantee would require a local buffer that repeats failed transmissions, and such a 
buffer works with asynchronous transmission as well. 
The measurement therefore supports the choice of fire and forget transmission described in 
Section~\ref{sec:impl-transport}.

\section{Threats to Validity}\label{sec:validity}

The preceding sections reported what the measurements show. 
This section states what they do not show, and why. 
The limitations are grouped by their origin, namely the measurement environment, the traffic 
used, the statistical basis, and the questions that the chosen setup cannot answer at all.

\subsection{Measurement Environment}\label{subsec:validity-environment}

The design described in Chapter~\ref{ch:system-design} places the monitoring backend outside 
the trust boundary of the IdP, which in a productive deployment would imply separate hosts under 
separate administrative control. 
The test environment does not realise this separation physically. 
All components run in containers on a single machine, which reproduces the logical separation 
of the components but not the security property derived from it. 
The measurements are therefore valid with respect to latency and correlation behaviour, but 
the environment does not demonstrate the trust boundary itself. 

The absolute values are therefore not transferable to a productive deployment. 
A login duration of approximately 360\,ms reflects this particular setup and would differ on 
separated hosts, under a different network topology or with a different user store. 
The differences between configurations are transferable to a greater degree, since they were 
measured in pairs within a single session and the shared conditions cancel out in the comparison.

The backend remained active during all runs, including the \textit{baseline} configuration in 
which the interceptors is not executed. 
This was deliberate, so that the background load would be identical across configurations. 
It also means that the measurements do not reflect a deployment in which no monitoring 
infrastructure is present at all.

\subsection{Traffic and Scope}\label{subsec:validity-traffic}

Most measurements rest on a single test user, a single SP and a single 
authentication flow, namely password-based authentication.
For the correlation this represents the hardest case with respect to candidate ambiguity, since 
all records share the same subject, the same address and the same SP, leaving time 
as the only distinguishing feature. 
With respect to temporal regularity it is the easier case, since a synthetic client produces more 
evenly spaced logins than real users. 
In a productive network the jitter would be larger and the operational limit derived in 
Section~\ref{subsec:interpretation-correlation} correspondingly lower. 
The offset statistic reported there is the figure by which this can be measured again in a 
different environment.

Several measurements use an HTTP client harness rather than a browser. 
Sections~\ref{subsubsec:precision-browser-traffic} and 
\ref{subsubsec:precision-multiple-browser-users} address this by repeating the measurement 
against real browser traffic, which showed the density effect to be reproducible while occurring 
considerably less often under realistic timing.

Single sign-on follow-up requests, in which an existing session is reused without a full 
authentication, were not measured. 
The interceptor would carry relatively more weight there, since the total latency of such a 
request is lower.

\subsection{Statistical Basis}\label{subsec:validity-statistics}

The performance evaluation rests on 18 runs per configuration, which yield 54 observations. 
The 95 percent confidence intervals of the latency contrasts have a half width of about 11\,ms, so 
that differences of this size or larger are established. 
The conclusion that the asynchronous mode introduces no measurable latency overhead is therefore a 
statement about an upper bound of about 17\,ms, or five percent of the median login duration, and 
not about the absence of any effect.
 
Six significance tests were performed without correction for multiple testing, namely three 
comparisons for the latency and three for the processor utilisation. 
The four significant results remain significant under a Bonferroni correction for six tests, whose 
threshold is 0.0083, with the weakest being the processor comparison between the synchronous and 
the asynchronous configuration, for which $p \approx 0.004$~\cite{Bonferroni}. 
The two comparisons that are not significant are unaffected.

The correlation measurements each rest on a single run, with sample sizes between 202 and 606 
reports. 
Precision is reported with Wilson score confidence intervals rather than the normal 
approximation, since the latter yields bounds outside the valid range or an interval of zero 
width where the observed precision reaches one hundred percent.

\subsection{What the Detection Figures Establish}\label{subsec:validity-detection}

The detection evaluation is subject to a limitation of a different kind, which concerns not the 
precision of the figures but their meaning.
Both the rules and the scenarios against which they are verified originate from the same source. 
A test that confirms a rule to behave as intended for a constructed case establishes the fidelity 
of the implementation. 
It does not establish that the rule detects genuine attacks, since the same understanding that 
produced the rule also produced the case.

This circularity is partially resolved and partially not. 
The derivation of the rules no longer rests on the author's judgement, since the vulnerabilities 
and attack classes they address are taken from the survey by Simpson and 
Groß~\cite{FIMSurvey} and from the OASIS security 
considerations~\cite{SAMLSecurityConsideration}. 
Which conditions are worth detecting is therefore determined externally. 
The verification of the rules, by contrast, remains internal.

Resolving it entirely would require productive traffic in which each login is independently 
labelled as malicious or benign. 
No such dataset exists for this work, and it cannot be produced within a test environment, since 
producing it would require the same judgement that the labelling is meant to verify. 

A partial measurement is nevertheless available. 
In 100 consecutive logins of three users against the clean SP, no alert of any type was raised, 
which bounds the proportion of legitimate logins that trigger an alert in this scenario to at most 
3.7 percent (95 percent Wilson interval). 
The measurement covers only an SP whose configuration is free of the weaknesses the rules are designed 
to detect, it uses a single browser, and it does not reach alerts that arise only after the retry 
window of fifteen minutes. 
It says nothing about the behaviour against configurations that are legitimate but unusual, which is 
the harder case in a production deployment. 

The false negative classes reported per rule are likewise derived rather than measured. 
Where a test deliberately carries a negative case, the statement is firm. 
Where a false negative class was inferred from the code path, it is plausible but not 
demonstrated by a failing test, since such a test would expose the same gap it describes.

The consistency check rests on a map that mirrors the abbreviations of the audit format of the 
IdP, for instance the notation of the status or of the authentication context. 
The backend holds a copy of the default map, which is not synchronised with the audit 
configuration of the IdP. 
Should an operator change the map there, the check would report deviations for values that are in 
fact consistent. 
The demonstration of the check rests on a single manipulation of a single field. 
It shows that the mechanism works but provides no detection rate.

A discrepancy alert cannot distinguish a counterpart that never arrives from one that arrives only 
after the retry window, for instance because of a delay in the log shipping chain. 
A report that has expired is not correlated again afterwards, so that such a late entry stays 
unmatched and the alert remains. 

\subsection{Derived but Not Validated}\label{subsec:validity-derived}

Two aspects of the system follow a documented derivation without having been validated 
empirically.
The severity levels follow the risk classification of Graves as described in 
Section~\ref{subsec:severity}. 
That the rules distinguish correctly between the levels is verified in several tests. 
Whether the resulting classification prioritises appropriately in operation is not verified, 
since this would require feedback from operators on alerts actually raised.

The numerical thresholds of several rules are point values chosen as plausible rather than 
determined by measurement. 
No sensitivity analysis was performed, meaning that the threshold at which a true positive turns 
into a false negative is unknown. 
Since the values were moved into the configuration during this work, such an analysis has become 
technically possible but remains outstanding.

\subsection{Known Gaps}\label{subsec:validity-gaps}

Three specific gaps are worth stating explicitly rather than leaving to be inferred.
\texttt{WEAK\_\allowbreak{}ENCRYPTION} has a true negative proof on layer two but no true positive proof, 
since establishing one would require an SP configured to use a weak algorithm. 

Nine of the fifteen rules are not covered by an explicit proof on layer two. 
As discussed in Section~\ref{subsec:detection-coverage}, five of them cannot sensibly be triggered 
through a normal login, three do not depend on a login at all, and the discrepancy rule raises 
its alert only after the retry window of fifteen minutes, which the end to end tests do not wait for. 

For the correlation, the case in which a shared source address and a missing user identifier 
coincide was not measured. 
Section~\ref{subsubsec:precision-nat} covers the shared address with the user identifier present, 
where the latter carries the entire separation. 
The combined case reduces methodologically to the density dependence of \texttt{TIME\_\allowbreak{}WINDOW} 
established throughout, rather than constituting an unknown of its own.
