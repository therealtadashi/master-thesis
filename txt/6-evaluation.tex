\chapter{Evaluation}\label{ch:evaluation}

This chapter evaluates the proposed monitoring system. 
It presents the test setup, evaluates the correlation and detection capabilities, 
measures the performance overhead introduced by the interceptor, and concludes 
with a discussion of the threats to validity. 

\section{Test Setup}\label{sec:setup}

To facilitate integration with the Java testing framework, the entire test environment 
runs in containers. 
This comprises the Shibboleth IdP, an LDAP directory serving as the user store, the SPs, 
and the backend application of the monitoring tool.

Two SPs are deployed. 
The first is used for the detection scenarios and is configured to exhibit the weaknesses 
that the rules are intended to identify. 
The second is configured according to current recommendations and serves as a reference for 
the false positive rate, since any alert raised for a login against this provider is by 
definition a false positive. 

The evaluation distinguishes three levels of testing. 
Unit tests examine individual components in isolation, with their dependencies replaced by 
mocks, so that a test result reflects the behaviour of that component alone. 
Integration tests run against a real Elasticsearch instance, which additionally covers the 
persistence layer, the index mappings and the queries that a mock cannot represent. 
End to end tests exercise the complete pipeline, from a login at the SP through the log 
shipping stack to the alert produced by the backend. 

Logins are generated in two ways. 
An HTTP client harness performs the SAML login sequence directly, parsing the forms returned 
by the IdP and submitting them without rendering the pages. 
Selenium based tests drive an actual browser through the same sequence. 
The two differ in the interval between consecutive logins, since the harness proceeds as fast 
as the server responds whereas a browser adds the time required for page loading and form 
interaction. 
This difference is relevant for the correlation measurements in Section~\ref{sec:eval-correlation}, 
where the temporal density of logins determines how reliably records can be matched.

The environment is not a production deployment. 
It comprises a single IdP, two SPs and a small number of test accounts, and all traffic is generated 
for the purpose of measurement. 
The implications of this are discussed in Section~\ref{sec:validity}.

\section{Correlation}\label{sec:eval-correlation}

Section~\ref{subsec:impl-correlation} explained the technical details of how the correlation 
algorithm worked. 
This Section presents the results of the correlation algorithm and the evaluation of the 
precision of the said algorithm. 

To calculate the precision of the less accurate correlation algorithms there has to be a data set 
which tells whether the correlation was correct or not. 
Luckily the correlation via the \texttt{INBOUND\_MESSAGE\_ID} produces a one to one correlation as 
explained in~\ref{subsec:impl-correlation}. 
Meaning this reliable correlation algorithm can be used as a ground truth for the subsequent 
correlation algorithms. 

Measurement method looks as follows:
\begin{itemize}
    \item Collect all interceptor reports for a configurable time period with \texttt{correlated\_by = INBOUND\_MESSAGE\_ID}
    \item For each report and each window size, execute the exact query of the heuristic strategy and select the same candidate (smallest time interval)
    \item Compare selected items with known correct audit IDs (Match / Incorrect assignment / No match)
    \item Additionally, output the time offset between custom interceptor flow reception and the actual audit event time as a distribution
\end{itemize}

The underlying data sources are 200 consecutive logins by a test user via the HTTP login harness. 
In terms of candidate ambiguity, this is the worst-case scenario. 
All candidates share the same \textit{subjectHash}, \textit{ipHash}, and \textit{SP}. 
Meaning time is the only distinguishing feature. 
For worm up purposes an additional three logins are performed before the consecutive 200 logins. 

\subsection{Findings of the Evaluation}\label{subsec:eval-correlation-findings}

Before the evaluation, 3,690 out of 3,690 correlations ran via the hashed identity and time window 
correlation algorithm, and not a single one via \texttt{INBOUND\_MESSAGE\_ID}. 
This was caused by the IdP's audit format (\textit{conf/audit.xml}, \textit{shibboleth.AuditFormattingMap}) did 
not contain \texttt{\%I}. 
The Logstash pipeline was already mapping \textit{[shib][I]} to \texttt{INBOUND\_MESSAGE\_ID}, but was waiting for 
a field that was never provided in the configuration. 
The precondition of the field registry expecting the inbound message id remained permanently unmet. 
After adding \texttt{\%I} to the audit format, the registry recognized the field, and the strategy activated 
itself, without a restart of the system. 
This is direct evidence of dynamic field adaptation. 

The time window strategies were compared against \textit{timestamp} attribute, which is Filebeat's ingest time, 
which is assigned per batch. 
Measurement based on benchmark traffic, found out that 2,423 audits were distributed across only 448 different 
\textit{timestamp} values, averaging 5.4 events per timestamp. 
Within a batch group, the time interval is identical for all candidates, thus, the chronological order of multiple 
logins could not be reconstructed. 

This was resolved by a new field \textit{event\_time}, which Logstash generates from \texttt{\%T} (IdP event time) 
using the date filter. 
Both time window strategies have been using this ever since. 
\textit{timestamp} remains unchanged as the basis for scheduler markers and the grace period—where the ingest time 
is factually correct. 

\subsection{Results of the Evaluation}\label{subsec:eval-correlation-results}

In the case of the temporal resolution introduced by the \textit{timestamp}, the alternative 
method of \textit{event\_time} resulted in 1.0 events per timestamp. 
Meaning each event had a unique timestamp, in contrast to the 5.4 events per timestamp caused 
by using \textit{timestamp}. 
These are the precision of the heuristic against the exact ground truth.

\subsubsection{Precision of TIME\_WINDOW under True Candidate Ambiguity (Multi-User)}\label{subsubsec:precision-time-window-multi-user}

The measurement in Table~\ref{tab:event-time-precision} are based on a single test user. 
In that case, the candidate sets for the hash identity and time window and time window algorithms 
are identical because a second \textit{usernameHash} never occurs during the observation period. 
As a result, the time window algorithm is never actually tested, only tracked. 
To address this, the same measurement methodology was applied to a dataset with multiple test 
users active in parallel.

In the expanded data set with three different users, each with 200 logins, launched simultaneously 
against the same SP with 600 reports in total. 
The ground truth was cleared before the run to prevent mixing with the single-user data. 
The results are summerized in Table~\ref{tab:precision-strategies}.

The precision of \texttt{TIME\_WINDOW} is identical across all six measured window sizes 
at 65\%. 
This follows directly from the selection rule the smallest time interval wins. 
Once the correct candidate is within the window, an additional, more distant candidate 
from a larger window can no longer displace it. 
Since no match is consistently 0, the \textpm 1s window was sufficient to include the correct 
candidate, just not always as the closest one.

The precision within the critical < 100ms zone is nearly identical for real and synthetic 
traffic (\~56-60\%). 
The weakness measured in Section~\ref{subsubsec:precision-time-window-multi-user} is therefore 
not an artifact of HTTP client timing, but a reproducible density effect. 
What differs is how often this zone is actually reached. 
The artificially timed stress test from Section~\ref{subsubsec:precision-time-window-multi-user} 
lands within it 87\% of the time, whereas three actual concurrent browser users do so only 23\% 
of the time. 
The lower overall precision in Section~\ref{subsubsec:precision-time-window-multi-user} thus 
accurately describes the stress test but exaggerates its frequency in the measured everyday operation.
The offset (\texit{receivedAt} - \textit{event\_time}) ranges from -158 to +42 ms (n = 606), which is 
by far the widest range of all sub-measurements, plausibly due to three parallel browser containers 
sharing CPU time.
